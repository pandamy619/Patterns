# 10. Prefix Sums (префиксные суммы)

## Суть в двух предложениях

Префиксная сумма — это сумма первых `t` элементов массива; посчитав такие суммы
один раз за O(n), мы получаем сумму **любого** отрезка как разность двух чисел.
Паттерн сводится к одной формуле: вопрос про отрезок превращается в вопрос
про пару префиксов, а с парой чисел уже умеют работать и простая арифметика,
и хеш-таблица.

```text
sum(nums[i..j]) = prefix[j + 1] - prefix[i]
```

Та же мысль работает не только для сложения. Нужна лишь операция, которую
можно накапливать слева направо: произведение, XOR, счётчик «сколько единиц
встретилось». Если у операции есть обратная (вычитание для суммы, XOR для XOR),
отрезок получается из двух префиксов. Если обратной нет или ею нельзя
пользоваться (деление при нулях) — берём префикс слева и суффикс справа.

## Как узнать паттерн

- в условии звучит **«сумма на отрезке»**, «сумма подмассива», «между индексами»;
- запросов **много**, а массив между ними **не меняется**;
- нужно **посчитать** подмассивы с заданной суммой (или с суммой, кратной
  чему-то, или с равным числом нулей и единиц — это та же задача после замены);
- в массиве есть **отрицательные числа**, и скользящее окно из-за этого ломается;
- ответ для позиции зависит от **всего, что слева**, и **всего, что справа**;
- наивное решение заново суммирует один и тот же кусок массива в цикле.

Контрпример: массив **меняется между запросами** («прибавь 5 к элементу 3,
потом спроси сумму»). Одно изменение портит все префиксы правее него, то есть
обновление стоит O(n). Здесь нужно дерево Фенвика или дерево отрезков:
и запрос, и обновление за O(log n).

## Что нужно знать про сложность

| Подход | Подготовка | Запрос суммы | Изменить элемент |
|---|---|---|---|
| считать каждый раз заново | — | O(n) | O(1) |
| префиксные суммы | O(n) | O(1) | O(n) |
| дерево Фенвика / дерево отрезков | O(n) | O(log n) | O(log n) |

Префиксные суммы выигрывают, когда данные статичны. Память — O(n) на массив
префиксов; иногда его можно не хранить целиком, а держать одну «бегущую»
сумму (приёмы 2 и 3).

## Три приёма

### 1. Prefix array (массив префиксных сумм)

Заводим массив на **один элемент длиннее** исходного: `prefix[t]` — сумма
первых `t` элементов, `prefix[0] = 0` — сумма пустого префикса.

```text
индекс          0    1    2    3    4    5
nums       =  [ 4   -2    7    1   -5    3 ]
prefix     =  [ 0    4    2    9   10    5    8 ]
индекс          0    1    2    3    4    5    6

сумма nums[1..3]:   prefix[4] - prefix[1]
                    (4 - 2 + 7 + 1) - (4)  =  10 - 4  =  6
```

```python
prefix = [0]
for value in data:
    prefix.append(prefix[-1] + value)

def range_sum(i, j):                 # обе границы включены
    return prefix[j + 1] - prefix[i]
```

Можно обойтись массивом той же длины, что и исходный (`prefix[i]` — сумма
по индекс `i` включительно), но тогда запрос с `i = 0` требует отдельной ветки.
Ведущий ноль убирает её, а вместе с ней — главный источник ошибок на единицу.

### 2. Prefix + hash map (префиксная сумма + хеш-таблица)

Когда отрезки нужно не суммировать, а **искать или считать**, переписываем
условие на языке префиксов:

```text
sum(nums[i..j]) = k    ⇔    prefix[j + 1] - prefix[i] = k    ⇔    prefix[i] = prefix[j + 1] - k
```

Получилась знакомая задача «найди партнёра для текущего числа» из темы 02:
идём слева направо, держим бегущую сумму и спрашиваем у таблицы, сколько раз
раньше встречался нужный префикс.

```python
seen = {0: 1}                        # пустой префикс уже «встретился»
running = 0
for value in data:
    running += value
    answer += seen.get(running - k, 0)
    seen[running] = seen.get(running, 0) + 1
```

Что класть в таблицу, зависит от вопроса: **счётчик** — если считаем отрезки,
**первый индекс** — если ищем самый длинный отрезок, просто **множество** —
если спрашивают «существует ли».

### 3. Prefix and suffix passes (проход слева и проход справа)

Если ответ для позиции `i` складывается из всего, что левее, и всего, что
правее, — считаем левую часть прямым проходом, правую обратным.

```text
nums   =  [  a    b    c    d  ]
слева  =  [  1    a    ab   abc ]      всё, что левее позиции
справа =  [ bcd   cd   d    1   ]      всё, что правее позиции
ответ  =  слева[i] * справа[i]
```

```python
result = [нейтральный] * n
left = нейтральный
for i in range(n):                   # слева направо
    result[i] = left
    left = объединить(left, data[i])
right = нейтральный
for i in reversed(range(n)):         # справа налево
    result[i] = объединить(result[i], right)
    right = объединить(right, data[i])
```

Правая часть нужна по одному элементу за раз, поэтому ей хватает переменной —
так получается O(1) дополнительной памяти.

### Сумма на отрезке

**Условие.** Дан массив целых чисел, он не меняется. Написать класс: конструктор
принимает массив, метод `sum_range(i, j)` возвращает сумму элементов с индексами
от `i` до `j`, **обе границы включены**. Запросов будет много.

**Идея.** Слово «много» — подсказка: платим один раз в конструкторе, чтобы
потом отвечать мгновенно. Строим массив префиксов с ведущим нулём; сумма
на отрезке — «первые `j + 1` элементов минус первые `i`».

**Почему корректно.** Первые `j + 1` элементов — это первые `i` элементов плюс
отрезок `[i, j]`. Вычитаем общую часть — остаётся отрезок. Отрицательные числа
ничему не мешают: мы нигде не опираемся на то, что суммы растут.

```text
nums   = [4, -2, 7, 1, -5, 3]
prefix = [0, 4, 2, 9, 10, 5, 8]

sum_range(1, 3) = prefix[4] - prefix[1] = 10 - 4 =  6     (-2 + 7 + 1)
sum_range(0, 2) = prefix[3] - prefix[0] =  9 - 0 =  9     (4 - 2 + 7) — без отдельной ветки
sum_range(4, 4) = prefix[5] - prefix[4] =  5 - 10 = -5    (один элемент)
sum_range(0, 5) = prefix[6] - prefix[0] =  8 - 0 =  8     (весь массив)
```

**Детали реализации.** Некорректный отрезок (`i > j`, выход за границы,
отрицательный индекс) вызывает `IndexError`. Без проверки Python принял бы
`-1` за «последний элемент» и молча вернул бы неверное число. Исходный массив
конструктор не изменяет и не хранит.

**Уточните в условии:** включена ли правая граница и может ли массив
меняться. Второй вопрос меняет структуру данных целиком (см. контрпример выше).

### Число подмассивов с суммой k

**Условие.** Дан массив целых чисел (**в том числе отрицательных и нулей**)
и число `k`. Сколько существует непрерывных непустых подмассивов с суммой
ровно `k`?

**Почему не скользящее окно.** Окно с двумя указателями держится на
монотонности: расширили окно — сумма выросла, сузили — уменьшилась. Поэтому
при сумме больше `k` можно смело сдвигать левую границу: «дальше будет только
больше». С отрицательными числами это неправда.

```text
nums = [4, -1], k = 3

окно [4]      сумма 4 > 3  → «перебор», сдвигаем левую границу, окно пустеет
окно [-1]     сумма -1
ответ окна: 0.  Правильный ответ: 1 — подмассив [4, -1]
```

Окно выбросило четвёрку, не зная, что следующая `-1` вернёт сумму к нужной.
Нули тоже мешают: для `[0, 0, 0]` и `k = 0` подходят все шесть подмассивов,
а окно в каждый момент видит только один.

**Идея.** Сначала честный промежуточный шаг: строим массив префиксов
и перебираем пары границ — O(n²), зато суммы отрезков уже за O(1).
Теперь смотрим на внутренний цикл: при фиксированном правом конце он ищет,
**сколько раз слева встретилось значение `prefix[end] - k`**. Поиск значения
среди уже пройденных — работа для хеш-таблицы. Храним `префиксная сумма →
сколько раз встретилась` и делаем один проход.

**Зачем в таблице изначально `{0: 1}`.** Подмассив — это «длинный префикс минус
короткий». Если подмассив начинается с индекса 0, то короткий префикс —
**пустой**, его сумма равна 0. Он существует всегда, ещё до первого элемента,
но сам в таблицу не попадёт: цикл записывает префиксы только после того, как
прочитал хотя бы один элемент. Поэтому кладём его руками. Без этого
`nums = [5], k = 5` даст 0 вместо 1. В приёме 1 ту же роль играет `prefix[0] = 0` —
это одна и та же идея.

**Почему счётчик, а не множество.** Одинаковые префиксные суммы встречаются
столько раз, сколько захотят: после куска с нулевой суммой бегущая сумма
возвращается к прежнему значению. Каждое такое вхождение — отдельная левая
граница и отдельный подмассив.

**Порядок действий.** Сначала спросить таблицу, потом записать текущий
префикс. Наоборот нельзя: при `k = 0` текущий префикс нашёл бы сам себя
и мы засчитали бы пустой подмассив.

```text
nums = [2, 1, -1, 3, -2, 2], k = 3

x =  2   running = 2   нужен -1   seen = {0:1}                    +0   count = 0
x =  1   running = 3   нужен  0   seen = {0:1, 2:1}               +1   count = 1
x = -1   running = 2   нужен -1   seen = {0:1, 2:1, 3:1}          +0   count = 1
x =  3   running = 5   нужен  2   seen = {0:1, 2:2, 3:1}          +2   count = 3
x = -2   running = 3   нужен  0   seen = {0:1, 2:2, 3:1, 5:1}     +1   count = 4
x =  2   running = 5   нужен  2   seen = {0:1, 2:2, 3:2, 5:1}     +2   count = 6
```

На втором шаге сработал именно пустой префикс: найден подмассив `[2, 1]`
от самого начала. На четвёртом — счётчик `2:2`: префикс с суммой 2 встречался
дважды, поэтому на тройке заканчиваются сразу два подмассива, `[1, -1, 3]` и `[3]`.

**Сложность.** Один проход, в нём два обращения к таблице — O(n) в среднем.
Разных префиксных сумм может быть до n + 1, отсюда O(n) памяти. В тестах есть
массив из 200 000 нулей: ответ — 20 000 100 000 подмассивов, и линейное решение
находит его мгновенно.

Оба решения — линейное и квадратичное — лежат в одном файле.

### Произведение всех, кроме текущего

**Условие.** По массиву целых чисел построить массив той же длины, где на
позиции `i` стоит произведение всех элементов, кроме `nums[i]`. Делить нельзя.
Время O(n), дополнительная память — O(1), массив ответа не в счёт.

**Почему напрашивается деление и что с ним не так.** Первая мысль: перемножить
всё и делить на `nums[i]`. Она ломается об ноль — на него делить нельзя,
а произведение всего массива при этом само равно нулю и никакой информации
не несёт. Поэтому запрет на деление в условии не каприз: он подталкивает
к решению, которому нули безразличны.

**Идея.** Убрать `nums[i]` из произведения — значит перемножить две части:
всё, что левее, и всё, что правее. Левая часть — префиксное произведение,
правая — суффиксное.

1. Проход слева направо: в `result[i]` кладём произведение `nums[0..i-1]`.
   Важен порядок внутри шага — **сначала записать, потом домножить** бегущее
   произведение на `nums[i]`, иначе элемент попадёт в собственный ответ.
2. Проход справа налево: бегущее произведение правой части живёт в одной
   переменной, на него домножаем `result[i]`.

Массив префиксов совмещён с массивом ответа, массив суффиксов сжат до
переменной — вот откуда O(1) дополнительной памяти.

```text
nums = [3, 2, 5, 4]

после прохода слева:    result = [1, 3, 6, 30]

i = 3   right =  1      result = [ 1,  3,  6, 30]
i = 2   right =  4      result = [ 1,  3, 24, 30]
i = 1   right = 20      result = [ 1, 60, 24, 30]
i = 0   right = 40      result = [40, 60, 24, 30]
```

**Нули.** Отдельной обработки в коде нет, и полезно понимать, почему она
не нужна. Случаев три.

- *Нулей нет.* Всё как в трассировке выше.
- *Ровно один ноль.* Для любой другой позиции ноль лежит либо слева, либо
  справа, попадает в одно из двух произведений — ответ 0. Для позиции самого
  нуля он не попадает никуда, и там получается произведение всех остальных.
- *Два нуля и больше.* Какую позицию ни возьми, хотя бы один ноль окажется
  слева или справа — весь ответ нулевой.

```text
nums = [3, 0, 5, 4]

после прохода слева:    result = [1, 3, 0, 0]      ноль «заразил» всё правее себя

i = 3   right =  1      result = [1,  3, 0, 0]
i = 2   right =  4      result = [1,  3, 0, 0]
i = 1   right = 20      result = [1, 60, 0, 0]     позиция нуля: 3 · (5 · 4)
i = 0   right =  0      result = [0, 60, 0, 0]     теперь ноль «заразил» всё левее
```

**Если бы делить разрешили.** Хороший дополнительный вопрос. Считаем число
нулей и произведение ненулевых элементов, дальше те же три случая: нет нулей —
делим; один ноль — всё нули, кроме его позиции; два и больше — все нули.
Этот вариант тоже лежит в файле (`product_array_with_division`) и проходит
те же тесты. В языках с фиксированной разрядностью у него есть ещё один
минус: общее произведение переполняется раньше, чем частичные.

**Края.** Для массива из одного элемента ответ `[1]` — произведение пустого
набора множителей; это стоит отметить, потому что `[0]` тоже превращается
в `[1]`.

## Типичные ошибки

- **Ошибка на единицу в формуле.** С ведущим нулём сумма `[i, j]` — это
  `prefix[j + 1] - prefix[i]`, а не `prefix[j] - prefix[i]`. Проверяйте формулу
  на отрезке из одного элемента.
- **Забытый пустой префикс.** Нет `prefix[0] = 0` или `{0: 1}` — теряются все
  отрезки, начинающиеся с индекса 0. На случайных тестах заметно не сразу.
- **Записать префикс в таблицу до запроса.** При `k = 0` засчитывается пустой
  подмассив; ответ завышен ровно на n.
- **Множество вместо счётчика** в задаче про число подмассивов: повторяющиеся
  префиксные суммы схлопываются, ответ занижен.
- **Скользящее окно при отрицательных числах.** Работает на «хороших» тестах
  с положительными числами и молча врёт на остальных.
- **Префиксные суммы для изменяемого массива.** Каждое обновление — O(n);
  нужна другая структура данных.
- **Деление в задаче про произведение** — и падение на первом же нуле. Если
  деление всё-таки используется, нули считают отдельно.
- **Перепутан порядок «записать → домножить»** в проходах: элемент попадает
  в собственное произведение.
- **Переполнение.** В Python целые числа безразмерны, но в Java или C++
  префиксные суммы длинного массива требуют 64-битного типа — скажите об этом.
