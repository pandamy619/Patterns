# 06. Binary Search (бинарный поиск)

## Суть в двух предложениях

Бинарный поиск — это не «поиск числа в отсортированном массиве», а способ
найти **границу**: место, где ответ на вопрос «да/нет» меняется с одного
на другой. Один вопрос к середине выбрасывает половину кандидатов, поэтому
из n вариантов остаётся один за O(log n) шагов.

Идею знают все, а пишут без ошибок немногие: вся сложность сидит в четырёх
мелких решениях — какие взять границы, `<` или `<=` в цикле, куда сужаться
и в какую сторону округлять `mid`. Эта тема — про то, как принимать их
не наугад, а по правилу.

## Как узнать паттерн

- данные **отсортированы** — целиком или «почти» (сдвиг по кругу, строки матрицы);
- в условии требуют **O(log n)** или n настолько велико, что O(n) не пройдёт;
- ищем **первый/последний** элемент с каким-то свойством, место вставки, границу;
- вопрос звучит как **«наибольшее X, при котором ещё…»** или **«наименьшее X,
  при котором уже…»**, и при этом умеем быстро проверить конкретное X;
- свойство **монотонно**: если X подходит, то подходят и все X по одну сторону от него;
- наивное решение — линейный проход по массиву или по всем возможным ответам.

Контрпример: «найти пару с суммой `target` в неотсортированном массиве» или
«найти любой элемент больше 10 в произвольном массиве». Нет порядка — нет
способа по одному элементу понять, какую половину выбросить. Сортировать ради
одного запроса невыгодно: O(n log n) хуже линейного прохода.

## Модель: лента из False и True

Любую задачу на бинарный поиск полезно привести к одному виду. Придумываем
предикат `good(i)` — вопрос с ответом «да/нет» — такой, чтобы на диапазоне
кандидатов он менялся **ровно один раз**:

```text
нижняя граница (ищем ПЕРВЫЙ True)        верхняя граница (ищем ПОСЛЕДНИЙ True)

 F  F  F  F  T  T  T  T                   T  T  T  T  T  F  F  F
             ^                                        ^
           ответ                                    ответ
```

Дальше остаются четыре решения, и каждое принимается механически.

| Решение | Правило |
|---|---|
| Границы `lo`, `hi` | Диапазон `[lo, hi]` обязан содержать **все возможные ответы**, включая ответ «ничего не нашлось». Отсюда `hi = n` в нижней границе и `lo = -1` в верхней |
| Условие цикла | Ищем границу → `while lo < hi`: цикл кончается, когда остался один кандидат, `lo == hi` — это ответ. Ищем точное совпадение с `return` изнутри → `while lo <= hi`: диапазон из одного элемента ещё нужно проверить |
| Куда сужаться | `mid` может быть ответом → оставляем его: `hi = mid` или `lo = mid`. `mid` точно не ответ → выбрасываем: `lo = mid + 1` или `hi = mid - 1` |
| Округление `mid` | Смотрим на строку **без** единицы. Есть `hi = mid` → округляем вниз. Есть `lo = mid` → округляем **вверх**: `(lo + hi + 1) // 2` |

Почему последнее правило спасает от бесконечного цикла. Опасен ровно один
момент — когда в диапазоне осталось два элемента:

```text
lo = 4, hi = 5

округление вниз:   mid = 4 = lo   →  ветка «lo = mid» ничего не меняет   ✗ вечный цикл
округление вверх:  mid = 5 = hi   →  ветка «hi = mid» ничего не меняет   ✗ вечный цикл
```

`mid` должен указывать на тот конец, который **сдвинется** при любом исходе:
при `hi = mid` / `lo = mid + 1` — на нижний, при `lo = mid` / `hi = mid - 1` —
на верхний. Тогда диапазон на каждом шаге строго уменьшается.

## Четыре приёма

### 1. Exact match (поиск точного совпадения)

Классика: три исхода сравнения, ответ возвращается прямо из цикла.

```python
lo, hi = 0, len(data) - 1
while lo <= hi:                  # <= : диапазон из одного элемента тоже проверяем
    mid = (lo + hi) // 2
    if data[mid] == target:
        return mid
    if data[mid] < target:
        lo = mid + 1             # mid проверен и не подошёл — выбрасываем
    else:
        hi = mid - 1
return -1                        # диапазон опустел
```

Обе ветки сдвигают границу **мимо** `mid`, поэтому округление не важно
и зациклиться невозможно. Когда: «есть ли число», поиск в матрице, поиск
в сдвинутом массиве.

### 2. Lower bound (нижняя граница) — первый True

```text
good:   F  F  F  T  T  T   | (n)
        lo →         ← hi     hi = n означает «True нет вообще»
```

```python
lo, hi = 0, n                    # n — законный ответ «не нашлось»
while lo < hi:
    mid = (lo + hi) // 2         # есть hi = mid → округляем вниз
    if good(mid):
        hi = mid                 # mid подходит, но левее может быть ещё один True
    else:
        lo = mid + 1             # mid и всё, что левее, — False
return lo                        # lo == hi
```

`mid` всегда меньше `hi`, поэтому `good(n)` никогда не вызывается — «сторож»
существует только как число. Когда: место вставки, первое вхождение, первый
префикс не меньше заданного, минимальное X, при котором условие уже выполнено.

### 3. Upper bound (верхняя граница) — последний True

Зеркальное отражение предыдущего шаблона — отразить нужно **всё**, включая
округление.

```text
good:   (-1) |  T  T  T  F  F  F
  lo = -1 означает «True нет вообще»
```

```python
lo, hi = -1, n - 1               # -1 — законный ответ «не нашлось»
while lo < hi:
    mid = (lo + hi + 1) // 2     # есть lo = mid → округляем ВВЕРХ
    if good(mid):
        lo = mid                 # mid подходит, но правее может быть ещё один True
    else:
        hi = mid - 1             # mid и всё, что правее, — False
return lo
```

Когда: последнее вхождение, максимальное X, при котором условие ещё выполнено.

> В Python нет переполнения целых, поэтому `(lo + hi) // 2` безопасно.
> В Java/C++ пишут `lo + (hi - lo) / 2`, а для округления вверх —
> `lo + (hi - lo + 1) / 2`.

### 4. Binary search on the answer (бинарный поиск по ответу)

Массива, по которому ищем, может и не быть. Если ответ — число из диапазона
`[min_answer, max_answer]` и есть монотонная проверка «подходит ли X», то
ищем прямо по этому диапазону шаблоном 2 или 3.

```python
lo, hi = min_answer, max_answer
while lo < hi:
    mid = (lo + hi + 1) // 2     # ищем наибольшее подходящее → шаблон 3
    if хватает(mid):             # проверка стоит O(n)
        lo = mid
    else:
        hi = mid - 1
return lo
```

Сложность — O(n log M), где M — ширина диапазона ответов. Когда: «максимальная
высота пилы», «минимальная скорость, чтобы успеть», «минимальная грузоподъёмность».

### Индекс вставки

**Условие.** Массив отсортирован по возрастанию, повторов нет. Если `target`
в нём есть — вернуть его индекс, иначе — индекс, на который его нужно вставить,
чтобы порядок сохранился.

**Идея.** Два случая из условия — на самом деле один. И индекс найденного
числа, и место вставки — это **первая позиция, где `nums[i] >= target`**.
Предикат `nums[i] >= target` монотонен (F…F T…T), значит, это нижняя граница
в чистом виде.

**Почему `hi = len(nums)`.** Если `target` больше всех, его место — за последним
элементом. Это полноценный ответ, и правило «диапазон содержит все ответы»
заставляет включить его в границы. С `hi = len(nums) - 1` пришлось бы дописывать
особый случай после цикла.

```text
nums = [-4, 0, 3, 8, 15], target = 5

lo=0 hi=5   mid=2   nums[2]=3  <  5   → lo = 3
lo=3 hi=5   mid=4   nums[4]=15 >= 5   → hi = 4
lo=3 hi=4   mid=3   nums[3]=8  >= 5   → hi = 3
lo == hi == 3                         → ответ 3 (между 3 и 8)
```

### Первое и последнее вхождение

**Условие.** Массив отсортирован по неубыванию, числа могут повторяться.
Вернуть `[первый индекс, последний индекс]` числа `target` или `[-1, -1]`.

**Идея.** Обычный поиск с `return mid` при совпадении попадёт в *какое-то*
вхождение, а расходиться от него в стороны линейно — O(n) на массиве из
одинаковых чисел. Поэтому при совпадении **не останавливаемся**, а ищем две
границы двумя независимыми поисками:

- первое вхождение — первый индекс, где `nums[i] >= target` (шаблон 2);
- последнее вхождение — последний индекс, где `nums[i] <= target` (шаблон 3).

После первого поиска проверяем, что нашли именно `target`, а не просто что-то
большее; если нет — второй поиск не нужен.

```text
nums = [2, 5, 5, 5, 9, 9, 14], target = 5

первое вхождение (округление вниз):
lo=0  hi=7   mid=3   nums[3]=5 >= 5   → hi = 3
lo=0  hi=3   mid=1   nums[1]=5 >= 5   → hi = 1
lo=0  hi=1   mid=0   nums[0]=2 <  5   → lo = 1          first = 1

последнее вхождение (округление вверх):
lo=-1 hi=6   mid=3   nums[3]=5 <= 5   → lo = 3
lo=3  hi=6   mid=5   nums[5]=9 >  5   → hi = 4
lo=3  hi=4   mid=4   nums[4]=9 >  5   → hi = 3          last = 3
```

Посмотрите на последнюю строку: `lo=3, hi=4`. С округлением вниз получилось бы
`mid=3`, сработала бы ветка `lo = mid`, и состояние `lo=3, hi=4` повторялось бы
вечно. Это и есть та самая ловушка.

**Альтернатива.** Последнее вхождение можно получить и одной нижней границей:
это «первый индекс, где `nums[i] >= target + 1`», минус один. Для целых чисел
это работает и позволяет обойтись одним шаблоном, но зеркальный вариант полезно
уметь писать: в задачах «по ответу» трюк с `+ 1` недоступен.

### Высота пилы

**Условие.** `heights` — высоты деревьев. Пила выставляется на целую высоту `H`
и срезает у каждого дерева выше `H` всё, что над ней; деревья ниже остаются
нетронутыми. Найти **наибольшую** `H`, при которой суммарно срезано не меньше
`k`. Выше самого высокого дерева пилу не поднимают. В решении добавлено своё
соглашение: если даже под корень (`H = 0`) древесины меньше `k`, возвращаем `-1`.

**Идея.** Отсортированного массива здесь нет, зато есть монотонность: чем ниже
пила, тем больше древесины. Значит, предикат `срезано(H) >= k` выглядит как
T…T F…F на оси высот, и нужна его верхняя граница. Диапазон ответов —
от `0` до `max(heights)`, проверка одной высоты стоит O(n).

**Почему не перебор высот.** Он стоит O(n · M), а высоты могут быть порядка 10⁹.
Бинарный поиск задаёт всего около 30 вопросов.

**Почему не сортировка + префиксные суммы.** Так тоже можно, но это O(n log n)
времени, O(n) памяти и заметно больше кода. Поиск по ответу проще и не требует
ничего, кроме умения проверить кандидата.

```text
heights = [7, 2, 10, 5], k = 8

lo=0 hi=10   mid=5   срезано 2+0+5+0 =  7  <  8   → hi = 4
lo=0 hi=4    mid=2   срезано 5+0+8+3 = 16  >= 8   → lo = 2
lo=2 hi=4    mid=3   срезано 4+0+7+2 = 13  >= 8   → lo = 3
lo=3 hi=4    mid=4   срезано 3+0+6+1 = 10  >= 8   → lo = 4
lo == hi == 4                                     → ответ 4
```

### Поиск в сдвинутом массиве

**Условие.** Отсортированный по возрастанию массив без повторов «прокрутили»:
несколько первых элементов перенесли в конец. Вернуть индекс `target` или `-1`.

**Идея.** Целиком массив не отсортирован, но точка разрыва одна. Поэтому, где бы
ни оказался `mid`, **хотя бы одна из половин** `[lo, mid]` или `[mid, hi]` разрыва
не содержит и отсортирована честно. Узнать какая — одно сравнение:
`nums[lo] <= nums[mid]` означает, что слева разрыва нет.

Про отсортированную половину можно за O(1) сказать, лежит ли в ней `target`:
достаточно сравнить его с двумя концами. Если лежит — идём туда, если нет —
в другую половину (про неё мы ничего не знаем, но больше ему быть негде).

```text
nums = [11, 14, 20, 1, 4, 6, 9], target = 20

lo=0 hi=6   mid=3 (1)    11 > 1  → отсортирована правая [1..9];   20 не в ней → hi = 2
lo=0 hi=2   mid=1 (14)   11 <= 14 → отсортирована левая [11..14]; 20 не в ней → lo = 2
lo=2 hi=2   mid=2 (20)   совпадение                                → ответ 2
```

**Тонкости.** Здесь шаблон точного совпадения, значит `while lo <= hi` — иначе
последняя строка трассировки не выполнится и ответ потеряется. В проверке
`nums[lo] <= nums[mid]` нужен именно нестрогий знак: при `lo == mid` левая
«половина» состоит из одного элемента, и её надо считать отсортированной
(проверьте на `[2, 1]`, `target = 1`). С повторами приём ломается: при
`nums[lo] == nums[mid] == nums[hi]` непонятно, где разрыв.

### Локальный максимум

**Условие.** Соседние элементы массива различны. Вернуть индекс любого элемента,
который больше обоих соседей; за краями массива — «минус бесконечность»,
так что крайний элемент тоже может быть ответом.

**Идея.** Массив не отсортирован, и всё же бинарный поиск работает — хороший
пример того, что паттерну нужна не сортировка, а **право выбросить половину**.
Смотрим на пару `nums[mid]`, `nums[mid + 1]`:

- справа **подъём** → идём вправо. Подъём не может длиться вечно: либо он
  где-то сменится спуском (вот и вершина), либо дойдёт до края, а за краем −∞;
- справа **спуск** → по тем же причинам вершина есть слева, включая сам `mid`.

Это шаблон нижней границы с предикатом «дальше спуск». Предикат здесь
не монотонен на всём массиве, но инвариант «в `[lo, hi]` есть вершина»
сохраняется на каждом шаге — этого достаточно.

**Почему `hi = n - 1`, а не `n`.** Ответ всегда существует, «сторож» не нужен.
А из-за округления вниз `mid < hi`, поэтому `nums[mid + 1]` не выйдет за границу.

```text
nums = [3, 8, 12, 7, 9, 4, 1]

lo=0 hi=6   mid=3   7 < 9  подъём   → lo = 4
lo=4 hi=6   mid=5   4 > 1  спуск    → hi = 5
lo=4 hi=5   mid=4   9 > 4  спуск    → hi = 4
lo == hi == 4                       → ответ 4 (значение 9)
```

Индекс 2 (значение 12) — тоже верный ответ; алгоритм просто до него не дошёл.

### Случайный выбор с весами

**Условие.** Написать класс: в конструктор приходят неотрицательные целые веса,
метод `pick()` возвращает индекс `i` с вероятностью `weights[i] / sum(weights)`.

**Идея.** Кладём веса отрезками вплотную на числовую прямую и бросаем в неё
«дротик» — равномерно случайное целое от 1 до `total`. Чем длиннее отрезок,
тем чаще в него попадают, причём ровно пропорционально длине.

```text
weights = [3, 1, 4]        prefix = [3, 4, 8]

клетка:   1  2  3 | 4 | 5  6  7  8
индекс:   0  0  0 | 1 | 2  2  2  2
```

Правые концы отрезков — это префиксные суммы, и они не убывают. Клетка `dart`
принадлежит **первому** отрезку, у которого правый конец `>= dart`, — снова
нижняя граница. Без бинарного поиска `pick()` стоил бы O(n); хранить массив
из `total` клеток — O(total) памяти, что при больших весах недопустимо.

```text
prefix = [3, 4, 8], dart = 4

lo=0 hi=2   mid=1   prefix[1]=4 >= 4   → hi = 1
lo=0 hi=1   mid=0   prefix[0]=3 <  4   → lo = 1
lo == hi == 1                          → индекс 1
```

**Тонкости.** Дротик берётся из `[1, total]`, а не из `[0, total]`: иначе
клеток станет `total + 1` и первый индекс получит лишний шанс. Нулевой вес даёт
отрезок нулевой длины — его префикс равен предыдущему, и нижняя граница всегда
выберет более раннего соседа, так что такой индекс не выпадет никогда.

**Как это тестировать.** Генератор передаётся в конструктор. В тестах вместо
него подставляется объект, который выдаёт подряд все значения от 1 до `total`, —
и результат сверяется с линейным поиском для каждого возможного броска.
Отдельный тест с `random.Random(2024)` проверяет, что на 60 000 бросков доли
сходятся к весам.

### Поиск в матрице

**Условие.** Каждая строка матрицы отсортирована по возрастанию, и первый элемент
строки больше последнего элемента предыдущей. Есть ли в матрице `target`?

**Идея.** Если выписать строки одну за другой, получится обычный отсортированный
массив длины `m · n`. Склеивать его не нужно: элемент с номером `i` лежит
в клетке `(i // cols, i % cols)`. Дальше — шаблон точного совпадения.

```text
matrix = [[ 1,  4,  6],
          [ 9, 13, 17],
          [20, 28, 35]],  target = 20

lo=0 hi=8   mid=4 → клетка (1, 1) = 13  < 20   → lo = 5
lo=5 hi=8   mid=6 → клетка (2, 0) = 20         → найдено
```

**Альтернатива.** Два поиска: сначала по первому столбцу найти строку, потом
искать внутри неё. Сложность та же — log m + log n = log(mn), — но кода вдвое
больше и вдвое больше мест для ошибки на единицу. Важно не спутать с матрицей,
где отсортированы строки и столбцы, но строки **не продолжают** друг друга
(LeetCode 240): там виртуальный массив не отсортирован, и нужен «спуск
по лестнице» из угла за O(m + n).

## Типичные ошибки

- **`lo = mid` вместе с `(lo + hi) // 2`.** Бесконечный цикл на диапазоне
  из двух элементов. На больших тестах может не проявиться, на `[1, 2]` — сразу.
  Правило: `lo = mid` → `mid` округляется вверх.
- **`while lo <= hi` вместе с `hi = mid`.** При `lo == hi` получаем `mid == hi`,
  ничего не меняется — тоже вечный цикл. `<=` — только для шаблона, где обе
  ветки шагают мимо `mid`.
- **`while lo < hi` в поиске точного совпадения.** Последний оставшийся
  кандидат не проверяется; поиск `5` в массиве `[5]` вернёт `-1`.
- **`hi = n - 1` там, где ответом может быть `n`.** Индекс вставки «в самый
  конец» оказывается недостижим. Симметрично — `lo = 0` в верхней границе,
  когда подходящих элементов может не быть.
- **Выбросили `mid`, хотя он мог быть ответом** (`hi = mid - 1` в нижней
  границе). Ошибка на единицу, которая ловится только тестом на границе.
- **Остановка на первом совпадении при повторах.** Для «первого вхождения»
  совпадение — не повод выходить, а повод сужаться дальше.
- **Немонотонный предикат.** Прежде чем писать поиск по ответу, проверьте:
  «если X подходит, то X − 1 тоже подходит». Если это неправда — бинарный поиск
  тихо вернёт ерунду.
- **Строгий знак в сдвинутом массиве.** `nums[lo] < nums[mid]` вместо `<=`
  ломает случай `lo == mid`.
- **`(lo + hi) / 2` в языках с переполнением.** В Python не страшно,
  но в C++ и Java сумма может переполниться — там пишут `lo + (hi - lo) / 2`.
