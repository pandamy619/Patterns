# 17. Sort and Search (сортировка и поиск)

## Суть в двух предложениях

Сортировка — это способ один раз заплатить O(n log n) и получить **порядок**,
после которого работают бинарный поиск, два указателя, слияние интервалов
и десяток других приёмов. Обе главные сортировки построены по принципу
«разделяй и властвуй»: merge sort делит тупо, а думает при слиянии; quicksort
думает при делении (partition), а склеивать ему уже нечего.

«Поиск» в названии темы — это поиск **порядковой статистики**: k-го по величине
элемента. Если нужен один-единственный элемент, сортировать весь массив —
перебор: quickselect делает то же разбиение, что и quicksort, но каждый раз
идёт только в одну из частей и в среднем укладывается в O(n).

## Как узнать паттерн

- вас прямо просят **реализовать сортировку** — массива или связного списка,
  без встроенных функций;
- данные лежат в **связном списке**, индексов нет → merge sort;
- нужен **k-й по величине / по малости** элемент, **медиана**, «топ-k»
  в готовом массиве, который целиком лежит в памяти → quickselect;
- значения — целые числа из **узкого диапазона** (оценки, возрасты, цвета,
  байты) → counting sort за линейное время;
- нужно **разбить массив на зоны** по условию («меньше / равно / больше»,
  «чётные / нечётные», «0 / 1 / 2») на месте → partition;
- речь заходит про **стабильность**, **худший случай** или «а что,
  если массив уже отсортирован?» — это вопросы именно из этой темы.

Контрпример: данные приходят **потоком**, и k-й по величине нужен после каждого
нового элемента. Quickselect каждый раз начинал бы заново за O(n); здесь нужна
куча размера k (см. тему 08). И второй: если реализация сортировки не является
сутью задачи, а нужен просто отсортированный вход для двух указателей или
интервалов, — вызывайте `sorted` и не изобретайте велосипед.

## Сравнение сортировок

n — число элементов, r — ширина диапазона значений (`max - min + 1`),
d — число разрядов в ключе.

| Сортировка | В среднем | В худшем | Доп. память | Стабильна | Когда вспоминать |
|---|---|---|---|---|---|
| Insertion sort (вставками) | O(n²) | O(n²) | O(1) | да | почти отсортированный вход — тогда O(n); маленькие куски внутри гибридных сортировок |
| Selection sort (выбором) | O(n²) | O(n²) | O(1) | нет | только как учебный пример; минимум обменов — n − 1 |
| Merge sort (слиянием) | O(n log n) | O(n log n) | O(n) для массива; O(log n) или O(1) для списка | да | связные списки, внешняя сортировка файлов, нужна стабильность и гарантия по времени |
| Quicksort (быстрая) | O(n log n) | O(n²) | O(log n) — стек | нет | массив в памяти; на практике самая быстрая из-за работы на месте и дружбы с кэшем |
| Heapsort (пирамидальная) | O(n log n) | O(n log n) | O(1) | нет | нужна и гарантия по времени, и O(1) памяти |
| Counting sort (подсчётом) | O(n + r) | O(n + r) | O(n + r) | да* | целые ключи из узкого диапазона |
| Radix sort (поразрядная) | O(d · (n + r)) | O(d · (n + r)) | O(n + r) | да | целые числа или строки фиксированной длины; внутри — стабильный counting sort по каждому разряду |
| Timsort (`sorted` в Python) | O(n log n) | O(n log n) | O(n) | да | всё, что не про реализацию сортировки; на почти отсортированных данных — O(n) |

\* Стабильна версия с префиксными суммами, которая расставляет исходные
записи по местам. Упрощённой версии для «голых» чисел (как в
[sort_array.py](sort_array.py)) стабильность не нужна: одинаковые числа
неразличимы.

Две вещи, которые стоит помнить наизусть:

- **Быстрее O(n log n) сравнениями нельзя.** У n элементов n! перестановок,
  каждое сравнение делит множество возможных ответов максимум пополам, значит
  сравнений нужно не меньше log₂(n!) ≈ n log n. Counting и radix sort этот
  барьер обходят, потому что не сравнивают элементы, а используют их как индексы.
- **Стабильность** — равные по ключу элементы сохраняют исходный порядок.
  Она важна, когда сортируют записи, а не числа: отсортировали заказы по дате,
  потом стабильно по клиенту — внутри клиента даты остались по порядку.

## Четыре приёма

### 1. Merge sort (сортировка слиянием)

Делим пополам, сортируем половины рекурсивно, сливаем два отсортированных
куска одним проходом. Вся содержательная работа — в слиянии.

```text
        [7 2 9 4 1]                 делим, пока не останется по одному
        /         \
    [7 2 9]      [4 1]
     /   \        /  \
  [7 2]  [9]    [4]  [1]
   / \
 [7] [2]
   \ /
  [2 7]  [9]    [1 4]               сливаем на обратном ходе рекурсии
     \   /        |
    [2 7 9]     [1 4]
         \       /
        [1 2 4 7 9]
```

```python
def merge_sort(data):
    if len(data) <= 1:
        return data
    mid = len(data) // 2
    left, right = merge_sort(data[:mid]), merge_sort(data[mid:])

    merged, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:            # «<=» — ради стабильности
            merged.append(left[i]); i += 1
        else:
            merged.append(right[j]); j += 1
    return merged + left[i:] + right[j:]
```

Уровней рекурсии log n, на каждом суммарно сливается n элементов — отсюда
O(n log n) **всегда**, без худших случаев. Цена — O(n) памяти под слияние
массивов. У связного списка этой цены нет: слияние — просто перестановка ссылок.

### 2. Partition (разбиение) и quicksort

Выбираем опорный элемент (pivot) и переставляем массив так, чтобы слева от него
оказалось всё меньшее, справа — всё большее. После этого pivot стоит **на своём
окончательном месте**, а левая и правая части сортируются независимо.

В этой теме используется разбиение на **три** зоны — «меньше», «равно»,
«больше». Три индекса режут массив на четыре отрезка:

```text
  lo          lt          i           gt          hi
  | < pivot   | == pivot  | ? ? ? ? ? | > pivot   |
              ^           ^           ^
  первая ячейка       текущий      последняя ячейка
  зоны «равно»        элемент      неразобранной части
```

```python
def partition_three_way(nums, lo, hi, pivot):
    lt, i, gt = lo, lo, hi
    while i <= gt:
        if nums[i] < pivot:
            nums[lt], nums[i] = nums[i], nums[lt]
            lt += 1
            i += 1
        elif nums[i] > pivot:
            nums[i], nums[gt] = nums[gt], nums[i]
            gt -= 1                    # i на месте: приехал непросмотренный элемент
        else:
            i += 1
    return lt, gt                      # nums[lt..gt] == pivot
```

Трассировка на `[5 9 5 2 8 1 5 7]`, pivot = 5:

```text
                                    массив                  lt  i  gt
старт                               [5  9  5  2  8  1  5  7]   0  0  7
5 = 5: i++                          [5  9  5  2  8  1  5  7]   0  1  7
9 > 5: обмен i↔gt, gt--             [5  7  5  2  8  1  5  9]   0  1  6
7 > 5: обмен i↔gt, gt--             [5  5  5  2  8  1  7  9]   0  1  5
5 = 5: i++                          [5  5  5  2  8  1  7  9]   0  2  5
5 = 5: i++                          [5  5  5  2  8  1  7  9]   0  3  5
2 < 5: обмен lt↔i, lt++, i++        [2  5  5  5  8  1  7  9]   1  4  5
8 > 5: обмен i↔gt, gt--             [2  5  5  5  1  8  7  9]   1  4  4
1 < 5: обмен lt↔i, lt++, i++        [2  1  5  5  5  8  7  9]   2  5  4   → i > gt, стоп

итог:  [2  1 | 5  5  5 | 8  7  9]    lt = 2, gt = 4
        < 5     == 5      > 5
```

Обратите внимание на строки с `9` и `7`: после обмена с правым краем `i` не
сдвигается, потому что на его место приехал элемент, который мы ещё не видели.
При обмене с `lt` такой проблемы нет: слева приезжает элемент из зоны «равно»
(или сам `nums[i]`, если зона пуста), про него всё известно.

Сам quicksort поверх разбиения — три строки:

```python
def quicksort(nums, lo, hi):
    if lo >= hi:
        return
    pivot = nums[random.randint(lo, hi)]
    lt, gt = partition_three_way(nums, lo, hi, pivot)
    quicksort(nums, lo, lt - 1)
    quicksort(nums, gt + 1, hi)
```

**Почему pivot случайный.** Время quicksort целиком зависит от того, насколько
ровно pivot делит массив. Если каждый раз пополам — уровней log n, итого
O(n log n). Если каждый раз откалывается один элемент — уровней n, итого
n + (n−1) + (n−2) + … = O(n²), а глубина рекурсии n роняет программу
с `RecursionError` задолго до того, как станет заметна медлительность.

- Правило «pivot = последний (или первый) элемент» даёт этот худший случай
  на **уже отсортированном** массиве — а это не экзотика, а один из самых
  частых входов в реальной жизни.
- Правило «pivot = средний» чинит отсортированный вход, но для **любого**
  фиксированного правила можно построить вход, который его ломает. Если вход
  приходит извне, это готовая атака на отказ в обслуживании.
- Случайный pivot переворачивает ситуацию: плохим теперь может быть не *вход*,
  а *бросок кубика*. Для любого входа ожидаемое время — O(n log n), а чтобы
  получить O(n²), нужно неудачно выбрать pivot почти на каждом уровне —
  вероятность этого убывает экспоненциально с ростом n.

Интуиция, почему «в среднем» хватает: pivot не обязан быть медианой. С шансом
1/2 он попадает в среднюю половину значений и делит массив не хуже чем 1 : 3.
Даже при таких делениях глубина — log₄⁄₃ n, то есть всё ещё O(log n).

**Почему три зоны, а не две.** Классическое двухзонное разбиение (схема Lomuto)
короче:

```python
def partition_lomuto(nums, lo, hi):        # pivot заранее переставлен в nums[hi]
    border = lo                            # слева от border — элементы меньше pivot
    for i in range(lo, hi):
        if nums[i] < nums[hi]:
            nums[border], nums[i] = nums[i], nums[border]
            border += 1
    nums[border], nums[hi] = nums[hi], nums[border]
    return border                          # окончательная позиция pivot
```

Но на массиве из одинаковых элементов оно всегда даёт деление «0 и n − 1» —
это тот же квадрат, и случайный pivot от него не спасает. Трёхзонное разбиение
убирает все копии pivot за один раз, и массив из одинаковых чисел сортируется
за один проход.

### 3. Quickselect (быстрый выбор)

Нужен элемент, который стоял бы на позиции `target` в отсортированном массиве.
После разбиения про зону «равно» известно всё — она на окончательном месте.
Значит, достаточно сравнить `target` с её границами:

```text
           lt        gt
  [ < pivot | == pivot | > pivot ]

  target < lt        → ответ слева, правую часть и зону «равно» выбрасываем
  lt <= target <= gt → ответ найден: это pivot
  target > gt        → ответ справа, выбрасываем левую часть
```

```python
def quickselect(nums, target):             # target — индекс в отсортированном массиве
    lo, hi = 0, len(nums) - 1
    while True:
        pivot = nums[random.randint(lo, hi)]
        lt, gt = partition_three_way(nums, lo, hi, pivot)
        if target < lt:
            hi = lt - 1
        elif target > gt:
            lo = gt + 1
        else:
            return pivot
```

Перевод формулировок в `target`: k-й по величине → `n - k`; k-й по малости →
`k - 1`; медиана → `n // 2`.

**Откуда O(n), если внутри тот же partition.** Quicksort после разбиения
обрабатывает **обе** части, поэтому на каждом уровне рекурсии суммарно n работы,
уровней log n. Quickselect идёт только в **одну** часть, и при сносном pivot
она в постоянное число раз меньше предыдущей:

```text
quicksort:    n + (n/2 + n/2) + (4 · n/4) + …  = n · log n
quickselect:  n +  n/2        +  n/4      + …  ≤ 2n
```

Геометрическая прогрессия сходится — отсюда линейное время в среднем. Худший
случай тот же, что у quicksort: pivot каждый раз откалывает один элемент,
n + (n−1) + … = O(n²). Лекарство то же — случайный pivot. Рекурсия не нужна:
отрезок только сужается, хватает цикла и O(1) памяти.

> Существует и детерминированный выбор pivot — «медиана медиан», он даёт O(n)
> в худшем случае. Достаточно знать, что он есть: константа
> у него большая, и на практике побеждает рандомизация.

**Quickselect или куча размера k?**

| | Quickselect | Min-куча размера k |
|---|---|---|
| Время | O(n) в среднем, O(n²) в худшем | O(n log k) всегда |
| Память | O(1), если массив можно менять | O(k) |
| Портит вход | да (или нужна копия за O(n)) | нет |
| Поток данных | нет: нужен весь массив сразу | да: один проход, элементы можно забывать |
| Повторные запросы после добавления элементов | каждый раз заново | O(log k) на элемент |

Quickselect лучше, когда массив **готов и лежит в памяти**, запрос **разовый**,
а k — **не маленькое**: для медианы (k = n/2) куча — это фактически O(n log n),
а quickselect остаётся линейным. Приятный бонус: после quickselect все элементы
правее `target` не меньше ответа, то есть «топ-k без порядка» получен бесплатно.

Куча лучше, когда данные идут **потоком** или не помещаются в память, когда k
**мало** (log k — почти константа, а проход один и без перестановок), когда
вход нельзя менять или когда нужна **гарантия** по времени без оговорки
«в среднем».

### 4. Counting sort (сортировка подсчётом)

Если значения — целые числа из узкого диапазона, их можно не сравнивать,
а использовать как индексы: посчитать, сколько раз встретилось каждое,
и выписать значения по порядку.

```python
def counting_sort(nums):
    smallest = min(nums)
    counts = [0] * (max(nums) - smallest + 1)
    for value in nums:
        counts[value - smallest] += 1          # сдвиг: минимум попадает в ячейку 0

    result = []
    for offset, count in enumerate(counts):
        result.extend([smallest + offset] * count)
    return result
```

Время O(n + r): проход по массиву плюс проход по счётчикам. При r ≈ n это
честная линейная сортировка; при значениях до 10⁹ массив счётчиков не влезет
в память — возвращаемся к quicksort. Важна именно **ширина диапазона**, а не
величина чисел: `[10⁹, 10⁹ − 2]` сортируется тремя счётчиками.

### Отсортировать связный список

**Условие.** Дана голова односвязного списка. Вернуть голову того же списка,
отсортированного по возрастанию значений.

**Почему merge sort.** Quicksort и heapsort опираются на доступ по индексу,
а в списке добраться до i-го узла — это O(i). Merge sort индексы не нужны:
он умеет только «найти середину» и «слить два списка», и обе операции
на списке делаются одним проходом. Более того, список для него удобнее
массива — слияние не требует буфера, узлы просто перешиваются.

**Идея.**

1. *Найти середину и разорвать.* Медленный указатель идёт по одному узлу,
   быстрый — по два (тема 04). Быстрый стартует на шаг впереди (`head.next`),
   поэтому медленный останавливается на **последнем узле левой половины** —
   ровно там, где нужно обнулить `next`.
2. *Рекурсивно отсортировать* обе половины. Дно рекурсии — пустой список или
   один узел.
3. *Слить* через фиктивный узел `dummy`: на каждом шаге пришиваем к хвосту
   меньшую из двух голов; когда один список закончился, остаток второго
   пришиваем целиком.

**Почему такая сложность.** Поиск середины и слияние — O(длины куска). На каждом
уровне рекурсии куски в сумме дают n, уровней log n → O(n log n). Память —
только стек рекурсии, O(log n): новые узлы не создаются.

**Стабильность.** При равенстве берём узел из левой половины (`<=`), поэтому
равные значения не меняются местами. В тестах это проверяется по `id` узлов.

```text
7 → 2 → 9 → 4 → 1

разрез  [7 2 9] | [4 1]          slow остановился на 9, fast ушёл за конец
  разрез  [7 2] | [9]
    разрез  [7] | [2]
    слияние [7] + [2]       = [2 7]
  слияние [2 7] + [9]       = [2 7 9]
  разрез  [4] | [1]
  слияние [4] + [1]         = [1 4]
слияние [2 7 9] + [1 4]     = [1 2 4 7 9]

последнее слияние по шагам:
  2 vs 1 → берём 1        dummy → 1
  2 vs 4 → берём 2        dummy → 1 → 2
  7 vs 4 → берём 4        dummy → 1 → 2 → 4
  правый список пуст      пришиваем остаток: 1 → 2 → 4 → 7 → 9
```

**Вариант без рекурсии (bottom-up).** Частый дополнительный вопрос: «а можно
с памятью O(1)?». Можно, если идти снизу вверх: сначала считаем, что список
состоит из отсортированных кусков длины 1, и сливаем их попарно; затем куски
длины 2, 4, 8 — пока кусок не накроет весь список. Проходов log n, каждый O(n).

```text
исходный            7   2   9   4   1
ширина 1 → пары    [2   7] [4   9] [1]
ширина 2           [2   4   7   9] [1]
ширина 4           [1   2   4   7   9]
```

В коде это функция `sort_linked_list_bottom_up`: `_cut_after` отрезает кусок
нужной длины, `tail` помнит, куда пришивать следующий слитый кусок.

### Отсортировать массив

**Условие.** Дан массив целых чисел, отсортировать его по возрастанию.
Встроенной сортировкой пользоваться нельзя — иначе задача теряет смысл.

**Идея.** Quicksort со случайным pivot и разбиением на три зоны — приём 2.
Два решения в коде сверх шаблона:

- **Рекурсия только в меньшую часть.** После разбиения остаются две части.
  В меньшую уходим рекурсивно, большую обрабатываем тем же циклом `while`.
  Меньшая часть не длиннее половины отрезка, поэтому глубина стека не больше
  log n **при любых** pivot. Случайность защищает время, этот трюк — стек.
- **Pivot передаётся в разбиение значением, а не индексом.** Трёхзонному
  разбиению не нужно заранее переставлять pivot в край отрезка: все его копии
  сами соберутся в середине.

**Почему корректно.** После `partition_three_way` любой элемент левой части
меньше любого элемента средней, а средней — меньше правой. Средняя зона стоит
окончательно; левую и правую можно сортировать независимо: элементы между
частями уже не перемешаются. Отрезок каждой рекурсии строго короче
исходного (зона «равно» содержит хотя бы сам pivot), поэтому алгоритм
завершается.

Пример хода (pivot случайный, при другом броске картинка будет иной):

```text
[9  4  7  1  8  2  7  3]

[0..7] pivot=2 → [1 |2| 7  8  4  7  3  9]      зона «равно»: [1..1]
  [2..7] pivot=8 → [1  2  7  4  7  3 |8| 9]    зона «равно»: [6..6]
    [2..5] pivot=3 → [1  2 |3| 7  4  7  8  9]  зона «равно»: [2..2]
      [3..5] pivot=7 → [1  2  3  4 |7  7| 8  9]   обе семёрки встали разом

[1  2  3  4  7  7  8  9]
```

Отрезки длины 0 и 1 в схеме не показаны — там делать нечего.

**Counting sort как альтернатива.** Если в условии сказано «значения от −100
до 100» или «это возрасты людей» — это намёк на приём 4. `sort_array_counting`
возвращает новый массив:

```text
nums = [3, -1, 2, 3, 0, -1, 3]        min = -1, max = 3 → 5 счётчиков

значение:   -1   0   1   2   3
счётчик:     2   1   0   1   3

выписываем: -1 -1 | 0 | (единиц нет) | 2 | 3 3 3  →  [-1, -1, 0, 2, 3, 3, 3]
```

### K-й по величине элемент

**Условие.** Дан непустой массив и число k, 1 ≤ k ≤ n. Вернуть элемент, который
стоял бы на k-м месте в массиве, отсортированном по убыванию. В книге
гарантируется, что дубликатов нет; здесь решение их допускает и считает каждую
копию отдельным элементом (как в LeetCode 215): для `[9, 6, 6, 2]` второй
и третий по величине — оба 6.

**Наивно.** Отсортировать и взять `nums[n - k]` — O(n log n). Но нам нужен один
элемент, а не весь порядок.

**Идея (quickselect, приём 3).** Ищем, кто стоит на позиции `target = n - k`
в порядке возрастания. Разбиваем отрезок случайным pivot; зона «равно» встаёт
на окончательные позиции `[lt..gt]`. Если `target` внутри — ответ pivot. Если
левее — сужаем отрезок до левой части, если правее — до правой. Выброшенная
часть ответ содержать не может: все её элементы стоят по другую сторону
от уже зафиксированной зоны.

```text
nums = [14, 3, 22, 8, 17, 5, 11], k = 3   →  target = 7 − 3 = 4

lo=0 hi=6  pivot=11 → [3  5  8 |11| 17 22 14]   зона [3..3], 4 > 3 → lo = 4
lo=4 hi=6  pivot=22 → [3  5  8  11  17 14 |22|] зона [6..6], 4 < 6 → hi = 5
lo=4 hi=5  pivot=14 → [3  5  8  11 |14| 17 22]  зона [4..4], попали → ответ 14
```

Просмотрено 7 + 3 + 2 = 12 элементов; полная сортировка при этом не понадобилась,
хотя на таком крошечном примере массив и оказался упорядочен. (Pivot случайный:
при другом броске шаги будут другими, ответ — тем же.)

**Почему три зоны важны и здесь.** На массиве из одинаковых чисел двухзонное
разбиение отщипывает по одному элементу — получается O(n²), и на LeetCode 215
есть тест ровно на это. Трёхзонное собирает все копии pivot сразу, `target`
попадает в зону «равно», ответ — за один проход.

**Вариант с кучей.** Держим min-кучу из k самых больших элементов среди
просмотренных. Новый элемент сравниваем с вершиной — самым слабым из топ-k:
если он больше, заменяем вершину. В конце вершина и есть k-й по величине.

```text
k = 3               куча (вершина слева)
14  → вставка       [14]
 3  → вставка       [3, 14]
22  → вставка       [3, 14, 22]
 8  → 8 > 3, замена [8, 14, 22]
17  → 17 > 8, замена[14, 17, 22]
 5  → 5 ≤ 14, мимо  [14, 17, 22]
11  → 11 ≤ 14, мимо [14, 17, 22]      ответ: вершина = 14
```

Куча именно **min**, хотя ищем большое: выбрасывать нужно самого слабого
из кандидатов, значит он и должен лежать на вершине. Когда что выбирать —
см. таблицу в приёме 3.

### Флаг Нидерландов

**Условие.** Массив состоит только из 0, 1 и 2. Упорядочить его на месте
за один проход, без подсчёта количеств и без сортировки общего вида.

**Идея.** Это трёхзонное разбиение с pivot = 1 в чистом виде: нули — «меньше»,
единицы — «равно», двойки — «больше». `low` — где будет следующая ячейка для
нуля, `high` — для двойки, `i` — текущий элемент.

**Почему корректно.** Инвариант: `[0, low)` — нули, `[low, i)` — единицы,
`(high, n)` — двойки. Каждый шаг либо сдвигает `i`, либо уменьшает `high`,
то есть неразобранный отрезок `[i, high]` сокращается на единицу — ровно n
шагов. Когда он опустел, весь массив состоит из трёх зон в нужном порядке.

```text
                        массив             low i high
старт                  [2 0 1 2 1 0 0]      0  0  6
2 → обмен с high       [0 0 1 2 1 0 2]      0  0  5     i на месте!
0 → обмен с low        [0 0 1 2 1 0 2]      1  1  5
0 → обмен с low        [0 0 1 2 1 0 2]      2  2  5
1 → дальше             [0 0 1 2 1 0 2]      2  3  5
2 → обмен с high       [0 0 1 0 1 2 2]      2  3  4     i на месте!
0 → обмен с low        [0 0 0 1 1 2 2]      3  4  4
1 → дальше             [0 0 0 1 1 2 2]      3  5  4     i > high, стоп
```

Решение «посчитать нули, единицы и двойки и перезаписать массив» (counting
sort) тоже линейное, но это два прохода, и оно не годится, если в массиве
не числа, а записи с ключом 0/1/2.

## Типичные ошибки

- **Фиксированный pivot.** «Последний элемент» проходит примеры из условия
  и падает на отсортированном массиве из 10⁵ чисел — по времени или
  с `RecursionError`.
- **Двухзонное разбиение и много дубликатов.** Случайный pivot не помогает,
  если все элементы равны: деление всё равно «0 и n − 1». Нужны три зоны.
- **Сдвиг `i` после обмена с правым краем.** В трёхзонном разбиении справа
  приезжает непросмотренный элемент; если шагнуть дальше, он останется
  не в своей зоне. Ошибка тихая: массив «почти» отсортирован.
- **`while i < gt` вместо `i <= gt`.** Элемент на позиции `gt` ещё не просмотрен,
  отрезок `[i, gt]` закрыт с обеих сторон.
- **Бесконечная рекурсия на списке из двух узлов.** Если быстрый указатель
  стартует с `head`, а не с `head.next`, медленный доходит до второго узла,
  и «левая половина» — это снова весь список. Проверяйте деление на длинах 2 и 3.
- **Забыли разорвать список.** Без `slow.next = None` левая половина по-прежнему
  ведёт в правую, и рекурсия сортирует один и тот же хвост бесконечно.
- **`<` вместо `<=` при слиянии.** Результат отсортирован, но стабильность
  потеряна — при сортировке записей это уже баг.
- **Путаница с k.** «k-й по величине» — это индекс `n - k` по возрастанию,
  а не `k` и не `n - k - 1`. Проверка на k = 1 (максимум) и k = n (минимум)
  ловит ошибку сразу.
- **Max-куча вместо min-кучи** в задаче про k-й по величине: работает, но это
  heapify + k извлечений с памятью O(n), а не O(k), — и не годится для потока.
- **Counting sort без оглядки на диапазон.** Два числа, `0` и `10⁹`, — и массив
  счётчиков на гигабайты. Сначала спросите про ограничения на значения.
- **Отрицательные числа в counting sort.** Без сдвига на минимум `counts[-1]`
  в Python молча запишет в конец массива счётчиков.
