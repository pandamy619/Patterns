# 11. Trees (деревья)

## Суть в двух предложениях

Дерево устроено рекурсивно: каждый ребёнок — корень такого же дерева, только
поменьше. Поэтому почти любая задача решается одним вопросом: «что узел должен
**получить от родителя**, что **вернуть родителю** и что сделать сам?» — а весь
остальной код это обход, который задаёт этот вопрос каждому узлу ровно один раз.

Обходов два семейства. DFS (в глубину) идёт до листа и возвращается — он удобен,
когда ответ собирается из поддеревьев или зависит от пути из корня. BFS
(в ширину) идёт этажами — он нужен, когда в условии есть слово «уровень».

## Как узнать паттерн

- на входе `root`, а у узла есть `left` и `right` — тут гадать не приходится;
  вопрос только в том, **какой обход** выбрать;
- ответ для узла выражается через ответы для детей (высота, сумма,
  «найдено ли в поддереве») → **DFS, postorder**;
- вниз нужно нести накопленное по пути: границы, глубину, префикс → **DFS, preorder**;
- дерево — BST и нужен порядок по возрастанию → **DFS, inorder**;
- звучит «уровень», «ширина», «вид сбоку», «ближайший к корню» → **BFS**;
- нужно сравнить две структуры узел в узел (симметрия, равенство) → DFS
  по **паре** узлов одновременно.

Контрпример: «найти кратчайший путь между двумя произвольными узлами» или
«все узлы на расстоянии k от данного». Идти придётся и вверх, а ссылок на
родителя в дереве нет. Это уже задача на граф: сначала строим таблицу
родителей (или список смежности), затем обычный BFS из темы про графы.

## Словарь и сложность

```text
            8            ← корень, глубина 0          уровень 0
          /   \
         3     12        ← 3 — родитель для 1 и 6     уровень 1
        / \      \
       1   6      14     ← 1 и 14 — листья            уровень 2
          / \
         4   7                                        уровень 3
```

- **n** — число узлов, **h** — высота, **w** — наибольшее число узлов на уровне.
- Любой обход посещает каждый узел один раз: время **O(n)**.
- Память DFS — **O(h)** (стек вызовов или явный стек), память BFS — **O(w)** (очередь).
- В сбалансированном дереве h ≈ log n, а w доходит до n/2. В вырожденном
  («палка») — наоборот: h = n, w = 1. Отсюда практический вывод: DFS дешевле на
  широких деревьях, BFS — на длинных и тонких.
- Поиск, вставка и удаление в BST — O(h): O(log n) у сбалансированного
  и O(n) у вырожденного.

### Глубина рекурсии в Python

По умолчанию интерпретатор разрешает около 1000 вложенных вызовов. Дерево-«палка»
из 10⁴ узлов — и рекурсивный DFS падает с `RecursionError`, хотя алгоритм верный
(тест `test_invert_binary_tree_iterative_survives_deep_tree` это показывает).
Что с этим делать:

1. Писать рекурсию — она короче и понятнее, — но **помнить её цену**:
   память O(h); если дерево может быть вырожденным на десятки тысяч
   узлов, нужен явный стек.
2. Уметь переписать: preorder на стеке тривиален, inorder — чуть хитрее
   (шаблон ниже), а вот postorder на стеке громоздкий — для него проще идти BFS
   и обрабатывать узлы в обратном порядке либо хранить в стеке флаг «дети уже готовы».
3. `sys.setrecursionlimit(10**6)` — рабочий костыль для олимпиадного кода, но не
   решение: лимит защищает от переполнения настоящего стека C, и на очень глубоком
   дереве можно получить не исключение, а падение интерпретатора.

Все BFS-решения этой темы и итеративные варианты DFS проверены на дереве
из 50 000 узлов в одну линию.

## Два приёма

### 1. DFS — Depth-First Search (обход в глубину)

Три порядка отличаются только тем, **когда узел делает свою работу** относительно
рекурсивных вызовов:

```python
def dfs(node, сверху):
    if node is None:
        return базовое_значение
    # preorder: работа ДО детей — есть только то, что пришло сверху
    слева = dfs(node.left, обновить(сверху, node))
    # inorder: работа МЕЖДУ детьми — левое поддерево уже пройдено целиком
    справа = dfs(node.right, обновить(сверху, node))
    # postorder: работа ПОСЛЕ детей — известны ответы обоих поддеревьев
    return собрать(node, слева, справа)
```

```text
        4              preorder  (узел, лево, право):  4 2 1 3 6
       / \             inorder   (лево, узел, право):  1 2 3 4 6
      2   6            postorder (лево, право, узел):  1 3 2 6 4
     / \
    1   3
```

Что когда выбирать:

| Порядок | Информация течёт | Берите, когда | Задачи темы |
|---|---|---|---|
| **Preorder (прямой)** | сверху вниз, через аргументы | решение в узле зависит от предков: допустимый интервал, глубина, накопленный путь; когда нужно скопировать или сериализовать дерево | BST Validation (интервал), Build from Preorder and Inorder, Rightmost Nodes (вариант на DFS) |
| **Inorder (центрированный)** | слева направо | дерево — BST: inorder выдаёт ключи по возрастанию, значит «k-й по величине», «проверить порядок», «соседние по значению» решаются одним проходом | BST Validation (вариант), Build… (inorder делит узлы на левых и правых) |
| **Postorder (обратный)** | снизу вверх, через `return` | ответ узла собирается из ответов детей: высота, сумма, «найден ли узел ниже»; удаление дерева | Balanced Validation, Lowest Common Ancestor, Maximum Path Sum |
| порядок не важен | — | операция в узле ни от кого не зависит | Invert Binary Tree |

Два полезных хода для postorder:

- **Возвращать одно, обновлять другое.** Родителю нужна одна величина («лучшая
  ветка вниз»), а ответом задачи является другая («лучший путь с изгибом»).
  Первая идёт через `return`, вторая — через `nonlocal`-переменную.
- **Сигнальное значение.** Вместо пары `(высота, сбалансировано)` можно
  возвращать высоту, а перекос кодировать как `-1`: настоящая высота
  отрицательной не бывает.

Итеративный inorder — единственный шаблон, который стоит помнить наизусть:

```python
stack, node = [], root
while stack or node:
    while node:                 # до упора влево, запоминая дорогу
        stack.append(node)
        node = node.left
    node = stack.pop()
    обработать(node)            # сюда попадаем в порядке inorder
    node = node.right
```

### 2. BFS — Breadth-First Search (обход по уровням)

Очередь плюс один трюк: **запомнить размер очереди до внутреннего цикла**.
В этот момент в ней лежит ровно один уровень; всё, что добавится в процессе, —
уже следующий.

```python
from collections import deque

queue = deque([root] if root else [])
while queue:
    level_size = len(queue)            # снимок: столько узлов на этом уровне
    for position in range(level_size):
        node = queue.popleft()
        обработать(node, position, level_size)
        if node.left:
            queue.append(node.left)
        if node.right:
            queue.append(node.right)
```

```text
уровень 0:   [8]
уровень 1:   [3, 12]           queue[0] — самый левый, queue[-1] — самый правый
уровень 2:   [1, 6, 14]
уровень 3:   [4, 7]
```

В очередь удобно класть не узел, а пару `(узел, метка)`: позицию в ряду
(Widest Level) или номер столбца (Binary Tree Columns). Обязательно `deque`:
у списка `pop(0)` стоит O(n), и обход незаметно становится квадратичным.

Когда BFS, а когда DFS: если нужен **порядок внутри уровня** или сам уровень как
единица — BFS. Если достаточно знать глубину узла, подойдёт и DFS с параметром
`depth` — так сделан второй вариант Rightmost Nodes.

### Отразить дерево зеркально

**Условие.** Поменять местами левое и правое у каждого узла и вернуть корень.

**Идея.** Отражение всего дерева — это обмен детей в **каждом** узле. Обмен
в одном узле никак не зависит от остальных, поэтому годится любой обход:
preorder, postorder, BFS — результат один и тот же. Отсюда два варианта:

- рекурсивный — одна строка `left, right = invert(right), invert(left)`;
- итеративный — стек узлов, у которых ещё не менялись дети.

Единственный порядок, на котором легко ошибиться, — inorder: после обмена
«правое» поддерево — это бывшее левое, уже обработанное, и оно будет отражено
дважды, а второе не будет отражено вовсе.

```text
[6, 2, 9, 1, None, 7]                  [6, 9, 2, None, 7, None, 1]

        6                                      6
       / \                                    / \
      2   9              →                   9   2
     /   /                                    \   \
    1   7                                      7   1
```

### Сбалансировано ли дерево

**Условие.** Дерево сбалансировано, если **в каждом** узле высоты левого
и правого поддеревьев отличаются не больше чем на 1. Вернуть `True`/`False`.

**Наивно.** В каждом узле вызвать `height(left)` и `height(right)`. Но `height`
сама обходит всё поддерево, и на «палке» получается n + (n−1) + … = O(n²).

**Идея.** Высота — типичная postorder-величина: `1 + max(левая, правая)`.
Раз она всё равно поднимается снизу вверх, проверяем баланс **там же, где
считаем высоту**, и каждое поддерево обходится один раз. Остаётся передать
наверх второй факт — «внутри уже есть перекос». Для этого хватает сигнального
значения `-1`: получив его от ребёнка, узел ничего не считает и просто передаёт
дальше. Заодно это ранний выход — правое поддерево можно даже не посещать.

**Почему нельзя проверить только корень.** В примере высоты поддеревьев корня
равны (3 и 3), но перекос спрятан глубже:

```text
[1, 2, 3, 4, None, None, 5, 6, None, None, 7]

          1
         / \
        2   3
       /     \
      4       5
     /         \
    6           7

узел 6:  лево 0, право 0   → высота 1
узел 4:  лево 1, право 0   → высота 2
узел 2:  лево 2, право 0   → |2 − 0| > 1, возвращаем −1
узел 1:  слева пришло −1   → сразу −1, правое поддерево не посещаем
ответ: False
```

### Вид на дерево справа

**Условие.** Вернуть значения узлов, которые видны, если смотреть на дерево
справа: по одному на уровень, сверху вниз.

**Идея.** «По одному на уровень» — это BFS. Самый правый узел уровня — тот,
что вышел из очереди последним, то есть `position == level_size - 1`.

**Ловушка.** «Идти всё время по правым детям» — неверно: когда правая ветка
обрывается, становятся видны узлы слева. В примере уровень 3 целиком принадлежит
левому поддереву.

```text
[3, 8, 5, 1, 6, None, None, None, None, 4]

        3        ← 3
       / \
      8   5      ← 5
     / \
    1   6        ← 6
       /
      4          ← 4

уровень 0:  [3]      → 3
уровень 1:  [8, 5]   → 5
уровень 2:  [1, 6]   → 6
уровень 3:  [4]      → 4
ответ: [3, 5, 6, 4]
```

**Вариант на DFS.** Обходим «узел → право → лево» и несём глубину. Первый узел,
попавший на ещё не виденную глубину, — самый правый на ней. Признак «глубина
новая» — `depth == len(result)`. Память O(h) вместо O(w), но рекурсия.

### Ширина самого широкого уровня

**Условие.** Ширина уровня — расстояние между его самым левым и самым правым
узлом, **считая пустые места между ними**. Вернуть наибольшую ширину.

**Идея.** Число узлов на уровне не годится: два узла могут стоять по краям
с дырой посередине. Нужны координаты. Нумеруем места так, как хранят кучу
в массиве: если узел стоит на месте `i`, его дети — на местах `2i` и `2i + 1`.
Тогда ширина уровня — `правый_номер − левый_номер + 1`, а пустые места
учитываются сами собой: им просто достались номера, которые никто не занял.

BFS даёт уровни, а крайние узлы — это `queue[0]` и `queue[-1]` в момент
«снимка» уровня.

**Про рост номеров.** Номера удваиваются с каждым уровнем: на глубине 64 они
не влезут в 64-битное целое. В Python переполнения нет, но арифметика над
числами в тысячи бит перестаёт быть O(1). Лечится одинаково: перед тем как
считать детей, вычитаем из номера номер левого края уровня. Разности внутри
уровня от сдвига не меняются, а номера остаются меньше ширины уровня.

```text
[1, 2, 3, 4, None, None, 5, 6]

          1
         / \
        2   3
       /     \
      4       5
     /
    6

уровень 0:  (1, место 0)                   ширина 0 − 0 + 1 = 1
уровень 1:  (2, место 0) (3, место 1)      ширина 1 − 0 + 1 = 2
уровень 2:  (4, место 0) (5, место 3)      ширина 3 − 0 + 1 = 4   ← ответ
уровень 3:  (6, место 0)                   ширина 0 − 0 + 1 = 1
```

На уровне 2 всего два узла, но между ними два пустых места — ширина 4.

### Корректно ли BST

**Условие.** Проверить, что для каждого узла **все** значения в левом поддереве
строго меньше него, а **все** в правом — строго больше.

**Ловушка.** Сравнивать узел только с его детьми недостаточно: ограничение
накладывают все предки. В примере `11 > 4` — с родителем всё в порядке,
но `11` лежит в левом поддереве `10`.

**Идея.** Каждому узлу положен открытый интервал `(low, high)`. У корня он
бесконечный. При спуске **влево** значение узла становится новым потолком,
при спуске **вправо** — новым полом. Это preorder: данные текут сверху вниз
через аргументы, узел проверяет себя раньше детей. Вместо `±inf` удобнее `None`
— не надо думать о диапазоне значений; только проверять его нужно через
`is not None`, иначе граница `0` сойдёт за отсутствующую.

```text
[10, 4, 15, 2, 11]

        10
       /  \
      4    15
     / \
    2   11

узел 10:  интервал (−∞, +∞)   ок
узел  4:  интервал (−∞, 10)   ок
узел  2:  интервал (−∞,  4)   ок
узел 11:  интервал ( 4, 10)   11 ≥ 10 → False
```

**Вариант на inorder.** У корректного BST центрированный обход строго возрастает.
Достаточно помнить одно предыдущее значение и проверять `текущее > предыдущего`.
В коде этот вариант итеративный — заодно пример шаблона со стеком.

**Дубликаты.** Здесь они считаются нарушением (как и в LeetCode 98). Если по
условию дубликаты разрешены с одной стороны — меняется одно из неравенств
на нестрогое; это нужно выяснить до того, как писать код.

### Наименьший общий предок

**Условие.** Даны два разных узла дерева. Найти самый глубокий узел, в поддереве
которого лежат оба. Узел считается предком самого себя.

**Идея.** Спросим у каждого поддерева: «есть ли в тебе что-нибудь из искомого?»
Это postorder — узел сначала выслушивает детей. Функция возвращает:

- `None`, если в поддереве нет ни одного из двух узлов;
- сам узел, если это один из искомых, — и **ниже не спускается**;
- если находки пришли **и слева, и справа** — текущий узел: пути к двум целям
  расходятся именно здесь, значит глубже общего предка нет;
- иначе — то единственное, что пришло снизу (одиночную находку или уже
  готовый ответ).

**Почему можно не спускаться ниже найденного узла.** Пусть встретили `first`.
Если `second` под ним — ответом будет сам `first`, и мы его как раз вернули.
Если `second` в другом месте — развилка выше, и ей нужен только факт
«слева что-то нашлось». В обоих случаях поддерево `first` ни на что не влияет.
Это опирается на гарантию, что оба узла в дереве действительно есть.

```text
[8, 3, 12, 1, 6, None, 14, None, None, 4, 7]      ищем LCA(1, 7)

            8
          /   \
         3     12
        / \      \
       1   6      14
          / \
         4   7

узел  1:  это цель                       → возвращает 1
узел  4:  слева None, справа None        → None
узел  7:  это цель                       → возвращает 7
узел  6:  слева None, справа 7           → 7
узел  3:  слева 1,    справа 7           → обе стороны: возвращает 3  ← LCA
узел 14:  слева None, справа None        → None
узел 12:  слева None, справа None        → None
узел  8:  слева 3,    справа None        → 3
ответ: узел 3
```

Узлы сравниваются **по ссылке** (`is`), а не по значению: в дереве с повторами
значений сравнение `==` нашло бы не тот узел.

### Дерево по preorder и inorder

**Условие.** Даны два обхода одного дерева с уникальными значениями: preorder
и inorder. Восстановить дерево.

**Идея.** Обходы дополняют друг друга:

- первый элемент **preorder** — корень;
- в **inorder** всё, что левее корня, — левое поддерево, всё, что правее, — правое.

Нашли корень, разделили, повторили для двух половин. Наивная реализация режет
списки срезами и ищет корень через `index()` — и то и другое O(n) на каждый
узел, итого O(n²). Оба расхода убираются:

1. **Хеш-таблица `значение → индекс в inorder`** строится один раз, поиск корня — O(1).
2. **Вместо срезов — границы `low..high`** в inorder и один общий указатель
   `next_root` по preorder. Он просто идёт слева направо: preorder — это
   «корень, затем всё левое поддерево, затем всё правое», поэтому, если
   строить **сначала левое** поддерево, к моменту построения правого указатель
   сам окажется на его корне.

Уникальность значений существенна: с повторами корень в inorder находится
неоднозначно, и дерево вообще не определено однозначно.

```text
preorder = [7, 2, 1, 5, 9, 8]     inorder = [1, 2, 5, 7, 8, 9]
индексы inorder: {1:0, 2:1, 5:2, 7:3, 8:4, 9:5}

build(0..5):  корень 7 (индекс 3)  → слева 0..2, справа 4..5
  build(0..2):  корень 2 (индекс 1)  → слева 0..0, справа 2..2
    build(0..0):  корень 1 — лист
    build(2..2):  корень 5 — лист
  build(4..5):  корень 9 (индекс 5)  → слева 4..4, справа пусто
    build(4..4):  корень 8 — лист

        7
       / \
      2   9          по уровням: [7, 2, 9, 1, 5, 8]
     / \ /
    1  5 8
```

Корни брались из preorder строго по порядку: 7, 2, 1, 5, 9, 8.

### Максимальная сумма пути

**Условие.** Путь — цепочка узлов, соединённых рёбрами, без развилок; может
начинаться и заканчиваться в любых узлах и не обязан проходить через корень.
В пути минимум один узел, значения бывают отрицательными. Найти максимальную сумму.

**Идея.** У любого пути есть **верхняя точка** — узел, ближайший к корню. Путь
выглядит как арка: из верхней точки вниз в левое поддерево и вниз в правое
(любая из двух частей может быть пустой). Переберём верхнюю точку — это каждый
узел по разу. Для узла лучшая арка:

```text
значение узла + max(0, лучшая ветка влево) + max(0, лучшая ветка вправо)
```

где «ветка» — путь, который идёт **только вниз**. Отсюда различие между тем, что
функция считает, и тем, что она возвращает:

- **ответ задачи** обновляется аркой — с обеими ветками;
- **родителю** возвращается `значение + max(левая, правая)` — только одна
  ветка. Путь, продолжающийся вверх к родителю, не может спуститься в обе
  стороны: получилась бы развилка.

`max(0, …)` означает «ветку с отрицательной суммой выгоднее не брать». При этом
сам узел входит в арку всегда, поэтому на дереве из одних отрицательных чисел
получится наибольшее из них, а не 0. По той же причине `best` стартует
со значения корня, а не с нуля.

```text
[2, 7, -4, 3, -6, 5, 1]

            2
          /   \
         7     -4
        / \    / \
       3  -6  5   1

узел  3:  ветки 0 и 0    арка   3    вернуть  3    лучший  3
узел −6:  ветки 0 и 0    арка  −6    вернуть −6    лучший  3
узел  7:  ветки 3 и 0    арка  10    вернуть 10    лучший 10    (−6 отброшена)
узел  5:  ветки 0 и 0    арка   5    вернуть  5    лучший 10
узел  1:  ветки 0 и 0    арка   1    вернуть  1    лучший 10
узел −4:  ветки 5 и 1    арка   2    вернуть  1    лучший 10    (вверх идёт только −4 + 5)
узел  2:  ветки 10 и 1   арка  13    вернуть 12    лучший 13
ответ: 13 — путь 3 → 7 → 2 → −4 → 5
```

Отрицательный узел −4 в ответ вошёл: он «стоит» 4, но открывает дорогу к 5.

### Вертикальный обход по столбцам

**Условие.** Корень стоит в столбце 0, левый ребёнок — на столбец левее
родителя, правый — правее. Вернуть значения по столбцам слева направо; внутри
столбца — сверху вниз, а узлы одной глубины — слева направо.

**Идея.** Номер столбца несём вместе с узлом, значения складываем в хеш-таблицу
`столбец → список`. Весь вопрос в порядке внутри списка. **BFS** посещает узлы
сверху вниз и слева направо — ровно в том порядке, который требуется, поэтому
достаточно дописывать в конец. DFS тут ошибается: в левом поддереве он может
уйти глубоко и попасть в столбец раньше, чем туда придёт мелкий узел из правого.

**Без сортировки.** Ключи таблицы нужно выдать по возрастанию. Сортировать
необязательно: номер столбца меняется на 1 за шаг, значит занятые столбцы
образуют сплошной отрезок. Запоминаем минимум и максимум и проходим
`range(leftmost, rightmost + 1)` — итого честные O(n).

```text
[1, 2, 5, None, 4, 3, None, None, 8]

столбцы:  -1   0   1
               1
             /   \
           2       5
             \   /
             4   3           4 и 3 оба в столбце 0, на одной глубине
              \
               8             8 — правый ребёнок узла 4, столбец 1

порядок BFS:  1(0)  2(−1)  5(+1)  4(0)  3(0)  8(+1)

столбец −1:  [2]
столбец  0:  [1, 4, 3]       4 левее 3, хотя значение у него больше
столбец +1:  [5, 8]          5 выше, чем 8; preorder-DFS записал бы 8 раньше
ответ: [[2], [1, 4, 3], [5, 8]]
```

### Симметрично ли дерево

**Условие.** Проверить, что дерево совпадает со своим зеркальным отражением
относительно вертикальной оси через корень.

**Идея.** Дерево симметрично, когда левое и правое поддеревья корня **зеркальны
друг другу**. Два поддерева `a` и `b` зеркальны, если:

- оба пусты; либо
- оба не пусты, `a.val == b.val`, и при этом `a.left` зеркально `b.right`
  (внешние края), а `a.right` зеркально `b.left` (внутренние края).

Это DFS, который идёт сразу по двум узлам. Итеративный вариант кладёт в очередь
такие же пары.

**Почему не «отразить и сравнить» и не «палиндром по уровням».** Первое работает,
но требует копии дерева — лишние O(n) памяти. Второе просто неверно, если
сравнивать только значения: форма тоже должна быть зеркальной.

```text
[5, 3, 3, None, 8, None, 8]

        5
       / \
      3   3            значения уровня 2: [8, 8] — «палиндром»,
       \   \           но обе восьмёрки висят справа
        8   8

пара (3, 3):        значения равны → проверяем внешние и внутренние края
  внешние  (3.left, 3.right) = (None, 8)   → пусто только с одной стороны
ответ: False
```

Для `[5, 3, 3, 1, 8, 8, 1]` все пары совпадают, ответ `True`.

## Типичные ошибки

- **Нет базового случая `node is None`.** Проще всего проверять пустоту в самом
  начале функции, а не перед каждым рекурсивным вызовом: проверок меньше,
  и пустое дерево на входе обрабатывается тем же кодом.
- **Пересчёт высоты в каждом узле.** Вызов `height()` внутри обхода даёт O(n²)
  на вырожденном дереве. Если величина нужна и детям, и родителю — возвращайте
  её из того же обхода.
- **BST: сравнение только с родителем.** Ограничения наследуются от всех предков.
  И не забудьте, что `if low:` ложно при `low == 0` — нужен `is not None`.
- **BFS: `len(queue)` в условии внутреннего цикла.** Очередь растёт по ходу
  цикла, и уровни сливаются. Размер снимается один раз, до цикла.
- **`list.pop(0)` вместо `deque.popleft()`.** Каждое извлечение — O(n).
- **Путь с развилкой.** В задаче о сумме пути вернуть родителю `val + left + right`
  — самая частая ошибка: такой «путь» содержит развилку.
- **`best = 0` в задаче о сумме пути.** На дереве из отрицательных чисел ответ
  станет нулём, хотя пустой путь не разрешён.
- **Сравнение узлов по значению.** В LCA ищут конкретные узлы: `is`, не `==`.
- **Симметрия без проверки формы.** `a is None or b is None` должно вести
  к ответу `a is b`, а не к `True`.
- **Порядок построения поддеревьев.** При общем указателе по preorder правое
  поддерево, построенное раньше левого, получит чужие корни. (Для пары
  postorder + inorder всё наоборот: идём с конца и строим сначала правое.)
- **Рекурсия на вырожденном дереве.** `RecursionError` на «палке» из 10⁴ узлов —
  см. раздел про глубину рекурсии.
