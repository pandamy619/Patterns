# 15. Dynamic Programming (динамическое программирование)

## Суть в двух предложениях

Динамическое программирование (DP) — это перебор, который **не делает одну и ту же
работу дважды**: большая задача выражается через такие же задачи поменьше, а их
ответы запоминаются. Вся сложность — не в коде (он обычно занимает десять строк),
а в том, чтобы правильно ответить на вопрос «что именно я запоминаю?».

Для DP нужны два свойства. **Перекрывающиеся подзадачи**: рекурсия снова и снова
приходит в одни и те же точки — иначе запоминать нечего, и это обычный «разделяй
и властвуй». **Оптимальная подструктура**: лучший ответ для целого собирается
из лучших ответов для частей — иначе запоминать бесполезно.

## Как узнать паттерн

- спрашивают **число**, а не сам объект: «сколько способов», «минимум / максимум»,
  «длина самой длинной…», «можно ли вообще»;
- решение строится как **цепочка выборов** (взять / пропустить, пойти вправо / вниз,
  какой монетой закончить), и каждый выбор оставляет задачу того же вида, но меньше;
- наивная рекурсия очевидна, но экспоненциальна, и в её дереве вызовов видны
  **повторяющиеся аргументы**;
- жадный выбор «бери лучшее прямо сейчас» ломается на маленьком контрпримере;
- ограничения намекают на O(n²) или O(n · W): n до нескольких тысяч, сумма или
  вместимость до 10⁴–10⁵.

Контрпример: «выведи **все** разбиения / все маршруты». Ответов экспоненциально
много, запоминание не спасёт — это Backtracking. И обратный случай: если жадный
выбор доказуемо верен (например, задачи на интервалы с сортировкой по концу),
DP сработает, но будет лишним — жадный алгоритм проще и быстрее.

## Метод: четыре вопроса

Любая DP-задача решается ответами на четыре вопроса — именно в таком порядке.
Дальше в конспекте каждая задача разобрана по этой схеме.

| Вопрос | Что нужно сформулировать | На примере лестницы |
|---|---|---|
| **Состояние** | Что означает `dp[i]` (или `dp[i][j]`) — одной фразой на русском | `ways[i]` — число способов попасть на ступень `i` |
| **Переход** | Как состояние выражается через меньшие: какой был **последний шаг**? | `ways[i] = ways[i-1] + ways[i-2]` |
| **База** | Состояния, где переход не работает; ответ для них известен без вычислений | `ways[0] = ways[1] = 1` |
| **Порядок** | В какой последовательности заполнять, чтобы всё нужное уже было готово | слева направо |

Несколько практических правил:

- **Состояние — это набор параметров, которые меняются в рекурсии.** Напишите
  рекурсию «в лоб», посмотрите на её аргументы — это и есть индексы таблицы.
  Размер таблицы = число разных наборов аргументов.
- **Если переход не получается — состояние неудачное.** Типичный ремонт: добавить
  условие «…и элемент `i` обязательно входит» (см. Кадане) или ещё одно измерение.
- **Думайте о последнем шаге, а не о первом.** «Каким ходом я попал сюда?» почти
  всегда даёт переход сразу.
- **Сложность** = число состояний × стоимость одного перехода. Память = число
  состояний (до оптимизации).
- **Ответ не всегда лежит в последней клетке.** У Кадане это максимум по всей
  таблице, у палиндрома — самый длинный отрезок с `True`.

### Top-down против bottom-up

```text
Top-down (мемоизация)                    Bottom-up (таблица)
рекурсия от ответа вниз + кэш            циклы от базы вверх, без рекурсии

  f(5)                                     dp: [1][1][2][3][5][8]
  ├─ f(4)                                       └──┴──►  ──►  ──►
  │  ├─ f(3) ...
  │  └─ f(2)  ← уже в кэше
  └─ f(3)     ← уже в кэше
```

| | Top-down | Bottom-up |
|---|---|---|
| Как писать | рекурсия + `@lru_cache` — почти дословно формула | циклы; порядок обхода нужно продумать самому |
| Какие состояния считает | только достижимые из ответа | все подряд |
| Слабое место | глубина рекурсии (в Python — ~1000 по умолчанию), накладные расходы на вызовы | легко ошибиться с порядком и границами |
| Оптимизация памяти | практически невозможна | естественная: выбрасываем старые строки |

Рабочая схема: **рекурсия → мемоизация → таблица → сжатие памяти**.
Первые два шага доказывают, что формула верна; вторые два — что вы умеете доводить
решение до промышленного вида. В [climbing_stairs.py](climbing_stairs.py) все четыре
шага выписаны подряд.

### Оптимизация памяти

Посмотрите, **на сколько шагов назад** смотрит переход:

- на 1–2 предыдущих значения → вместо массива хватит двух переменных
  (лестница, дома, Кадане);
- только на предыдущую строку таблицы → храним две строки или даже одну
  (сетка, LCS, рюкзак);
- на отрезки произвольной меньшей длины → сжать трудно (палиндромы) — ищите
  решение без таблицы.

При сжатии до одной строки клетка одновременно играет две роли — «старое значение
сверху» и «новое значение». Порядок обхода выбирают так, чтобы к моменту чтения
клетка хранила **то, что нужно переходу**: в сетке нужно новое значение слева —
идём слева направо; в рюкзаке 0/1 нужно старое значение слева — идём справа налево.

Цена сжатия: по сжатой таблице нельзя **восстановить сам ответ** (какие предметы
взяли, какая именно подпоследовательность) — для этого нужна полная таблица.

## Пять приёмов

### 1. 1D DP (линейная динамика)

Состояние — один индекс: префикс массива, номер ступени, сумма. Переход смотрит
на фиксированное число шагов назад либо перебирает небольшой набор вариантов.

```python
dp = [БАЗА] * (n + 1)
for i in range(1, n + 1):
    dp[i] = объединить(dp[i - шаг] for шаг in варианты)     # +, min, max
```

Если шагов назад фиксированное число `k` — массив заменяется `k` переменными.

### 2. Grid DP (2D DP по сетке)

Состояние — клетка `(r, c)`, переход — из соседних клеток, откуда разрешён ход.
База — первая строка и первый столбец. Обход построчно.

```text
        c-1    c
r-1   [     ][  ↓  ]
r     [  →  ][ r,c ]        dp[r][c] = dp[r-1][c] + dp[r][c-1]
```

```python
dp = [[1] * cols for _ in range(rows)]
for r in range(1, rows):
    for c in range(1, cols):
        dp[r][c] = dp[r - 1][c] + dp[r][c - 1]
```

Тот же каркас решает «минимальную стоимость пути» (`min` вместо `+`) и сетки
с препятствиями (в клетке-стене пишем 0).

### 3. Two-sequence DP (DP по двум строкам)

Состояние — пара **префиксов**: `dp[i][j]` — ответ для `a[:i]` и `b[:j]`. Нулевые
строка и столбец отданы пустым префиксам, поэтому таблица на единицу больше строк,
а символы читаются как `a[i - 1]`, `b[j - 1]`.

```python
dp = [[0] * (len(b) + 1) for _ in range(len(a) + 1)]
for i in range(1, len(a) + 1):
    for j in range(1, len(b) + 1):
        if a[i - 1] == b[j - 1]:
            dp[i][j] = dp[i - 1][j - 1] + 1
        else:
            dp[i][j] = max(dp[i - 1][j], dp[i][j - 1])
```

Так же устроены редакционное расстояние, кратчайшая общая надпоследовательность,
сопоставление с шаблоном.

### 4. Interval DP (DP по отрезкам)

Состояние — отрезок `[i..j]` одной строки, переход — через **более короткие**
отрезки. Отсюда главное правило: внешний цикл идёт **по длине**.

```text
      j → 0 1 2 3 4
i=0       ■ ① ② ③ ④        цифра — на каком проходе заполняется клетка
i=1         ■ ① ② ③        ■ — база (длина 1)
i=2           ■ ① ②
i=3             ■ ①        клетка [i][j] смотрит на [i+1][j-1] —
i=4               ■        по диагонали влево-вниз
```

```python
for length in range(2, n + 1):
    for i in range(n - length + 1):
        j = i + length - 1
        dp[i][j] = переход(dp[i + 1][j - 1], ...)
```

### 5. Take / skip (взять / не взять)

Элементы рассматриваются по одному, и для каждого ровно два исхода. Состояние —
«сколько элементов уже рассмотрено» плюс **ресурс**, который расходуется, если
элемент взять (вместимость, сумма, запрет на соседа).

```python
dp[i][ресурс] = max(
    dp[i - 1][ресурс],                              # пропустили
    dp[i - 1][ресурс - цена(i)] + польза(i),        # взяли
)
```

Если элемент можно брать **многократно** (монеты), во второй ветке стоит `dp[i]`
вместо `dp[i - 1]` — и в одномерной версии обход разворачивается слева направо.

### Подъём по лестнице

**Условие.** В лестнице `n` ступеней, за шаг можно подняться на одну или на две.
Сколько есть разных способов дойти до верха?

**Состояние.** `ways[i]` — число способов оказаться на ступени `i`.
**Переход.** Последний шаг был либо с `i-1`, либо с `i-2`; эти группы маршрутов
не пересекаются, поэтому `ways[i] = ways[i-1] + ways[i-2]`.
**База.** `ways[0] = 1` (стоим на месте — один «пустой» маршрут), `ways[1] = 1`.
**Порядок.** По возрастанию `i`.

**Четыре версии одного решения.**

1. *Рекурсия.* Формула, записанная буквально. Работает за O(φⁿ): для `n = 6`
   это 25 вызовов, для `n = 30` — уже 2 692 537.
2. *Мемоизация.* Добавляем `@lru_cache` — каждое `ways(i)` считается один раз, O(n).
3. *Таблица.* Убираем рекурсию: массив и цикл слева направо.
4. *Две переменные.* Переход смотрит только на два шага назад — остальной массив
   не нужен. O(1) памяти.

```text
n = 6

ступень   0   1   2   3   4   5   6
ways      1   1   2   3   5   8  13        каждое число — сумма двух слева
```

Это числа Фибоначчи со сдвигом на единицу. Сказать об этом полезно, но решение
должно выводиться из рассуждения о последнем шаге, а не из «я узнал Фибоначчи»:
стоит разрешить шаг на три ступени — и рассуждение по-прежнему работает, а узнавание нет.

### Минимум монет для суммы

**Условие.** Даны номиналы монет (каждой — сколько угодно) и сумма `target`.
Вернуть наименьшее число монет, дающих ровно `target`, либо `-1`, если набрать нельзя.

**Почему не жадность.** «Бери самую крупную» работает для привычных номиналов, но
не в общем случае: для `[1, 4, 6]` и суммы 8 жадность даст 6 + 1 + 1 (три монеты)
вместо 4 + 4.

**Состояние.** `fewest[a]` — минимум монет для суммы `a`.
**Переход.** Перебираем, какой монетой `c` закончили:
`fewest[a] = 1 + min(fewest[a - c])` по всем `c ≤ a`.
**База.** `fewest[0] = 0`; всё остальное изначально `∞` — «пока не умеем».
**Порядок.** По возрастанию суммы: `a - c` всегда меньше `a`.

**Почему `∞`, а не `-1`.** С бесконечностью не нужны особые случаи: `∞ + 1 = ∞`,
и `min` сам отбросит недостижимые суммы. В `-1` переводим один раз, на выходе.

```text
coins = [1, 4, 6], target = 8

сумма a     0   1   2   3   4   5   6   7   8
fewest[a]   0   1   2   3   1   2   1   2   2
последняя   -   1   1   1   4   1   6   1   4
монета

fewest[8] = min(fewest[7], fewest[4], fewest[2]) + 1 = min(2, 1, 2) + 1 = 2   → 4 + 4
```

Строка «последняя монета» в коде не хранится, но именно так восстанавливают сам
набор: от `target` шагаем назад по запомненным монетам.

**Сложность.** `target + 1` состояний, на каждое — цикл по `k` номиналам.
Top-down версия считает только достижимые остатки (для `[5, 7]` это заметно меньше),
но глубина рекурсии доходит до `target / min(coins)`.

### Число путей в сетке

**Условие.** Сетка `m × n`. Стартуем в левом верхнем углу, ходить можно только
вправо и вниз. Сколько разных маршрутов ведёт в правый нижний угол? `m, n ≥ 1`.

**Состояние.** `paths[r][c]` — число маршрутов из старта в клетку `(r, c)`.
**Переход.** В клетку входят либо сверху, либо слева:
`paths[r][c] = paths[r-1][c] + paths[r][c-1]`.
**База.** Первая строка и первый столбец — по единице: туда ведёт одна прямая дорога.
**Порядок.** Построчно, слева направо.

```text
m = 3, n = 4

1   1   1   1
1   2   3   4
1   3   6  10   ← ответ
```

**Сжатие до одной строки.** Переход смотрит на клетку сверху и клетку слева.
Если обновлять строку на месте слева направо, то в момент `row[c] += row[c - 1]`:

- `row[c]` ещё хранит значение прошлой строки — это «сверху»;
- `row[c - 1]` уже обновлён — это «слева».

Задача симметрична (`m × n` и `n × m` дают один ответ), поэтому строку ведём вдоль
короткой стороны — память O(min(m, n)). Для сетки 3 × 4 это строка из трёх клеток,
которая обновляется три раза (по сути, считаем ту же таблицу по столбцам):

```text
[1, 1, 1]  →  [1, 2, 3]  →  [1, 3, 6]  →  [1, 4, 10]
```

**Формула.** Любой маршрут — это `m - 1` ходов вниз и `n - 1` вправо в каком-то
порядке, значит ответ равен C(m + n − 2, m − 1). Упомянуть стоит, но DP-версия
важнее: она переживает усложнения (препятствия, стоимость клеток), а формула — нет.

### Дома без соседей

**Условие.** `houses[i]` — сколько денег в доме `i`. Сигнализация срабатывает,
если взять два соседних дома. Какую наибольшую сумму можно унести?

**Почему не жадность и не «через один».** Для `[10, 100, 10]` чётные позиции дают
20, а ответ — 100. Для `[70, 10, 10, 70]` выгодно пропустить сразу два дома подряд.

**Состояние.** `best[i]` — лучший результат на первых `i` домах (последний из них
брать **не обязательно**).
**Переход.** Про дом `i` есть два решения:

- пропустить → `best[i-1]`;
- взять → его деньги плюс `best[i-2]`, потому что сосед слева теперь запрещён.

`best[i] = max(best[i-1], best[i-2] + houses[i])`.
**База.** «Ноль домов» → 0. Сдвиг индексов на единицу избавляет от отдельных
проверок для одного и двух домов.
**Порядок.** Слева направо; нужны только два последних значения → O(1) памяти.

```text
houses = [60, 90, 50, 20, 80]

дом   деньги   пропустить   взять          best
 0      60         0         0 + 60  =  60   60
 1      90        60         0 + 90  =  90   90
 2      50        90        60 + 50  = 110  110
 3      20       110        90 + 20  = 110  110
 4      80       110       110 + 80  = 190  190   ← дома 0, 2, 4
```

**Почему состояние без «обязательно взят» здесь работает.** Запрет касается
только ближайшего соседа, и сдвиг на `i-2` его полностью учитывает: что бы ни
происходило среди первых `i-2` домов, дому `i` это не мешает.

### Наибольшая общая подпоследовательность

**Условие.** Даны две строки. Найти длину самой длинной последовательности символов,
которая встречается в обеих в том же порядке, но не обязательно подряд.

**Состояние.** `table[i][j]` — длина LCS для префиксов `a[:i]` и `b[:j]`.
**Переход.** Смотрим на последние символы префиксов:

- равны → `table[i-1][j-1] + 1`;
- не равны → хотя бы один из них в ответ не входит:
  `max(table[i-1][j], table[i][j-1])`.

**База.** Пустой префикс ни с чем ничего общего не имеет — нулевые строка и столбец.
**Порядок.** Построчно: нужны клетки сверху, слева и по диагонали.

**Почему при равенстве можно не рассматривать другие варианты.** Пусть последние
символы равны, а в оптимальном ответе `a[i-1]` спарен с каким-то более ранним
символом `b`. Тогда пару можно «пересадить» на `b[j-1]` — длина не изменится,
а порядок не нарушится, ведь правее в `b` уже ничего нет. Значит, решение,
где последние символы спарены друг с другом, не хуже любого другого.

```text
a = "кабан", b = "банка"

          ""   б   а   н   к   а
    ""     0   0   0   0   0   0
    к      0   0   0   0   1   1
    а      0   0   1   1   1   2
    б      0   1   1   1   1   2
    а      0   1   2   2   2   2
    н      0   1   2   3   3   3   ← ответ 3, подпоследовательность «бан»
```

**Память.** Строка `i` зависит только от строки `i-1` — достаточно двух строк,
а если вести их вдоль короткого слова, выходит O(min(m, n)).

**Восстановление.** Идём из правого нижнего угла: символы равны — записываем
и шагаем по диагонали, иначе — в сторону большего соседа. Для этого нужна полная
таблица (`restore_common_subsequence`).

### Самая длинная палиндромная подстрока

**Условие.** Вернуть самую длинную **подстроку** (символы идут подряд), которая
читается одинаково в обе стороны. Если таких несколько — в этом конспекте
возвращается самая левая; в условии порядок не оговорён, подойдёт любая.

Полный перебор — O(n³): O(n²) подстрок, каждая проверяется за O(n).

**Решение 1 — таблица по отрезкам.**

**Состояние.** `is_pal[i][j]` — правда ли, что `s[i..j]` палиндром.
**Переход.** Края совпадают **и** середина — палиндром:
`is_pal[i][j] = s[i] == s[j] and is_pal[i+1][j-1]`.
**База.** Отрезки длины 1 — всегда палиндромы; для длины 2 середина пуста,
достаточно равенства краёв.
**Порядок.** По возрастанию **длины**. Клетка `[i][j]` смотрит на `[i+1][j-1]` —
на строку *ниже*; обычный обход «по i сверху вниз» прочитал бы ещё пустые клетки.

```text
s = "abbac"            T — палиндром, . — нет (заполняется только i ≤ j)

       a  b  b  a  c
   a   T  .  .  T  .        [0][3] = «abba»: края a == a, середина [1][2] = «bb» — T
   b      T  T  .  .        [1][2] = «bb»:  длина 2, края равны
   b         T  .  .
   a            T  .
   c               T
```

Ответ — самый длинный отрезок с `T`. Время O(n²), память O(n²).

**Решение 2 — расширение от центра.** Палиндром симметричен относительно центра,
и центров у строки всего `2n - 1`: `n` символов (нечётная длина) и `n - 1`
промежутков (чётная). От каждого центра раздвигаем границы, пока символы совпадают.

```text
s = "abbac"

i    центр — символ s[i]    центр — промежуток между s[i] и s[i+1]
0          "a"                    ""         (a ≠ b)
1          "b"                    "abba"     ← лучший: bb → abba → дальше край строки
2          "b"                    ""         (b ≠ a)
3          "a"                    ""         (a ≠ c)
4          "c"                    ""         (правее ничего нет)
```

Те же O(n²) по времени, но O(1) по памяти — и на практике быстрее, потому что
расширение обрывается на первом несовпадении. По сути это та же DP: шаг расширения
и есть переход «середина — палиндром, края равны», просто значения не хранятся,
а используются сразу.

> Существует алгоритм Манакера за O(n). Достаточно знать, что он есть:
> в базовый набор он не входит.

### Наибольшая сумма подмассива

**Условие.** Дан непустой массив целых чисел. Найти наибольшую сумму непрерывного
подмассива (хотя бы из одного элемента).

**Первая попытка состояния не работает.** «`best[i]` — лучшая сумма на префиксе» —
из такого определения переход не построить: неизвестно, примыкает ли лучший
подмассив к позиции `i`, а значит, непонятно, можно ли его продолжить.

**Состояние.** `ending_here[i]` — лучшая сумма подмассива, который **заканчивается
ровно в `i`**.
**Переход.** Такой подмассив либо продолжает предыдущий, либо начинается заново:
`ending_here[i] = max(nums[i], ending_here[i-1] + nums[i])`. Иначе говоря, прежний
хвост берём с собой, только если он положительный.
**База.** `ending_here[0] = nums[0]`.
**Ответ.** Максимум по всем `i` — лучший подмассив где-то да заканчивается.
**Порядок.** Слева направо, хранится одно число.

```text
nums = [4, -6, 3, -1, 5, -8, 2]

x     ending_here              best
 4         4                     4
-6     4 - 6 = -2                4
 3     max(3, -2 + 3) = 3        4     хвост -2 отброшен, начали заново
-1     3 - 1 = 2                 4
 5     2 + 5 = 7                 7     ← [3, -1, 5]
-8     7 - 8 = -1                7
 2     max(2, -1 + 2) = 2        7
```

Обратите внимание на шаг с `-1`: отрицательный **элемент** — не повод обрывать
подмассив. Обрываем, только когда отрицательной стала накопленная **сумма**.

`maximum_subarray_with_bounds` дополнительно возвращает границы найденного подмассива.

### Рюкзак 0/1

**Условие.** Есть рюкзак вместимостью `cap` и предметы с весами `weights[i]`
и ценностями `values[i]`. Каждый предмет можно взять целиком или не брать вовсе.
Найти наибольшую суммарную ценность при суммарном весе не больше `cap`.

**Почему не жадность.** Сортировка по «ценности на килограмм» ошибается: при
`cap = 10`, весах `[6, 5, 5]` и ценностях `[66, 50, 50]` она хватает первый предмет
(11 за кг) и больше ничего не помещается — 66 вместо 100.

**Состояние.** `table[i][c]` — лучшая ценность, если разрешены первые `i` предметов
и вместимость равна `c`. Одного индекса мало: без второго параметра неизвестно,
сколько места осталось.
**Переход.** `table[i][c] = max(table[i-1][c], table[i-1][c - w] + v)`; вторая ветка
доступна при `w ≤ c`. Обе ветки читают строку `i-1` — именно это гарантирует,
что предмет `i` не окажется в рюкзаке дважды.
**База.** Строка 0 (предметов нет) — нули.
**Порядок.** По предметам, внутри — по вместимости.

```text
cap = 6, weights = [2, 3, 4], values = [30, 40, 60]

вместимость c         0    1    2    3    4    5    6
нет предметов         0    0    0    0    0    0    0
+ предмет 0 (2, 30)   0    0   30   30   30   30   30
+ предмет 1 (3, 40)   0    0   30   40   40   70   70
+ предмет 2 (4, 60)   0    0   30   40   60   70   90   ← предметы 0 и 2

table[3][6] = max(table[2][6], table[2][6 - 4] + 60) = max(70, 30 + 60) = 90
```

**Сжатие до одномерного массива и почему обход справа налево.** Строка `i` читает
из строки `i-1` клетку над собой и клетку **левее**. Если держать одну строку
и обновлять её на месте, клетка `c - w` к моменту чтения должна быть ещё старой.
Она лежит левее, значит идти нужно **справа налево**: всё, что левее текущей
позиции, пока не тронуто.

```text
один предмет (вес 2, ценность 30), cap = 6

c                  0    1    2    3    4    5    6
справа налево      0    0   30   30   30   30   30     верно: предмет один
слева направо      0    0   30   30   60   60   90     best[4] прочитал уже новое best[2],
                                                       предмет взят дважды, потом трижды
```

Обход слева направо — не «сломанный» алгоритм, а решение другой задачи: рюкзака
с **неограниченным** числом копий. Сравните с монетами выше — там цикл по суммам
как раз идёт по возрастанию, потому что монету разрешено брать повторно.

**Сложность.** O(n · cap) — псевдополиномиальная: она зависит от *значения* `cap`,
а не от длины его записи. Для `cap` порядка 10⁹ таблица не построится; задача
NP-трудная, и чуда здесь нет.

`zero_one_knapsack_items` восстанавливает набор предметов: идём по полной таблице
снизу вверх, и если `table[i][c] != table[i-1][c]`, предмет `i` был взят.

## Типичные ошибки

- **Состояние не сформулировано словами.** «`dp[i]` — ну, ответ для `i`» — так
  не пойдёт. Пока нет точной фразы («…заканчивается в `i`», «…на первых `i`
  элементах»), переход либо не выводится, либо выводится неверный.
- **Сдвиг индексов.** Таблица по префиксам на единицу больше данных: `dp[i]`
  соответствует символу `s[i - 1]`. Перепутать легко, а на тестах из одинаковых
  букв ошибка не видна.
- **Ноль вместо «невозможно».** В задачах на минимум незаполненные клетки должны
  быть `∞`, иначе ноль победит в любом `min`. И обратное: в Кадане нельзя начинать
  с `best = 0` — для массива из отрицательных чисел ответ станет нулём.
- **Порядок заполнения.** В DP по отрезкам внешний цикл — по длине. В сжатом
  рюкзаке 0/1 — справа налево, в монетах — слева направо. Ошибка тихая: код не
  падает, просто считает другую задачу.
- **Ответ взят не из той клетки.** `dp[n]` — не универсальное место: у Кадане
  и у палиндромов ответ — максимум по таблице.
- **Кэш по изменяемому аргументу.** `@lru_cache` требует хешируемых аргументов:
  передавайте индексы, а сами списки захватывайте замыканием.
- **Глубина рекурсии.** Top-down на 10⁴ ступеней упадёт с `RecursionError`.
  Поднимать `sys.setrecursionlimit` — костыль; надёжнее переписать в таблицу.
- **Путаница «подстрока / подпоследовательность».** Подстрока непрерывна,
  подпоследовательность — нет. Это разные задачи с разными переходами.
- **DP там, где хватает жадности или формулы** — и наоборот. Прежде чем отвергать
  жадный алгоритм, предъявите контрпример; прежде чем принять — доказательство.
